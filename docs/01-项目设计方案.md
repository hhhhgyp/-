# 智能行李寄存柜预约系统 —— 项目设计方案

> 版本：v1.0（设计稿，尚未编码）
> 目标：本地单机可运行、业务规则明确可验证、便于测试实践与面试讲解
> 明确约定：本文档中标注【未实现】的功能，指**本期不实现**，不属于当前验收范围

---

## 1. 业务背景与用户角色

### 1.1 业务背景

旅游景点、高铁站、火车站等场所存在大量「临时行李寄存」需求：游客到达后希望先把行李存起来再游玩，但传统人工寄存点存在排队、无柜、无法预约、无法提前规划的问题。

本系统把线下寄存柜搬到线上，提供**按时段预约柜格**的能力：

- 用户可以提前（最多 7 天）查看某寄存点在指定时间段是否还有空闲柜格；
- 用户根据行李尺寸选择合适规格的柜格并下单；
- 系统保证**同一柜格在同一时间段内只会被一个有效订单占用**；
- 用户到店后在规定时间内完成存入，超时未存入则系统自动释放资源；
- 管理员维护寄存点、柜体、柜格、规格与订单。

旅游景点/车站的特点是**潮汐式并发**：同一时间段大量游客抢同一批柜格。这正是本项目要制造并验证的核心测试场景（并发预约、资源竞争、超卖防护）。

### 1.2 用户角色

| 角色 | 标识 | 说明 | 主要权限 |
|---|---|---|---|
| 游客（未登录） | 匿名 | 只能浏览 | 查看寄存点、柜体、柜格规格、指定时间段的空闲柜格 |
| 普通用户 | `USER` | 已注册游客 | 注册/登录/登出、创建预约、查看自己订单、在规则内取消、签到、取件 |
| 管理员 | `ADMIN` | 运营人员 | 管理寄存点/柜体/柜格/规格、查看全部订单、强制取消、切换维护状态、手动触发超时释放任务 |
| 系统任务 | `SYSTEM` | 非人类角色 | 超时释放、逾期标记，写操作记为 `SYSTEM` 操作人 |

> 说明：**本期不做多租户和「寄存点管理员」细分角色**（即管理员是全局管理员），多租户权限模型列为【未实现】。

## 2. 完整业务流程

### 2.1 主流程（正常成功路径）

```
[游客] 浏览寄存点列表
   └─> 进入寄存点详情，选择「寄存开始时间 / 结束时间 / 行李尺寸」
        └─> 系统返回该时间段内可用的柜格列表（按规格分组）
             └─> [未登录] 跳转登录 / 注册
                  └─> [已登录] 选择某个柜格 -> 进入确认预约页
                       └─> 提交预约（携带客户端生成的 idempotency_key）
                            ├─ 成功 -> 生成订单，状态 = RESERVED（已预约）
                            └─ 失败 -> 展示明确错误（时段冲突 / 尺寸不匹配 / 柜格维护中…）
                                 └─> 刷新可用柜格后重新选择
[用户] 到店，在签到窗口内点击「签到存入」
   └─ 状态 RESERVED -> IN_USE（使用中）
[用户] 取走行李，点击「完成取件」
   └─ 状态 IN_USE -> COMPLETED（已完成），柜格时段资源释放
   └─ 在订单历史中可查询该订单
```

### 2.2 取消流程

```
[用户] 我的订单 -> 点击「取消预约」（仅 RESERVED 状态、且当前时间 <= 开始时间 - 30 分钟）
   ├─ 满足条件 -> 状态 -> CANCELLED，释放该订单占用的全部柜格时段，pay_status -> REFUNDED（模拟）
   └─ 不满足 -> 409 CANCEL_WINDOW_EXPIRED / ORDER_STATUS_NOT_ALLOWED
```

### 2.3 超时释放流程（系统）

```
[定时任务，每 60 秒] 扫描 status=RESERVED 且 checkin_deadline <= NOW() 的订单
   └─ 逐条加锁处理：状态 -> EXPIRED，释放柜格时段，写入状态变更日志
        └─ 该柜格的这些时段重新变为「可预约」
[定时任务，每 60 秒] 扫描 status=IN_USE 且 end_time < NOW() 的订单
   └─ 状态 -> OVERDUE（逾期未取件）
        └─ 注意：OVERDUE 仍然占用柜格（行李还在柜内），不会被自动释放
```

### 2.4 管理流程

```
[管理员] 登录 -> 进入管理控制台
   ├─ 寄存点管理：新增/编辑/启用停用
   ├─ 柜体管理：在寄存点下新增柜体（柜机）
   ├─ 柜格管理：在柜体下批量新增柜格、指定规格、切换 可用 / 维护中 / 停用
   ├─ 规格管理：新增/编辑柜格规格（尺寸等级、价格、是否启用）
   ├─ 订单管理：按条件检索订单、查看详情、强制取消（FORCE_CANCELLED）
   └─ 任务管理：查看超时释放任务执行日志、手动触发一次（用于测试重复执行）
```

### 2.5 订单状态机（唯一权威定义）

| 状态 | 中文 | 是否占用柜格 | 可执行操作 |
|---|---|---|---|
| `RESERVED` | 已预约（待签到） | 是 | 签到、用户取消、管理员强制取消、超时进 `EXPIRED` |
| `IN_USE` | 使用中 | 是 | 取件完成、到期末取转 `OVERDUE` |
| `OVERDUE` | 逾期未取件 | 是 | 取件完成（补取） |
| `COMPLETED` | 已完成 | 否（终态） | 无 |
| `CANCELLED` | 用户已取消 | 否（终态） | 无 |
| `EXPIRED` | 超时未签到自动释放 | 否（终态） | 无 |
| `FORCE_CANCELLED` | 管理员强制取消 | 否（终态） | 无 |

允许的状态转换（其余一律返回 `409 ORDER_STATUS_NOT_ALLOWED`）：

```
RESERVED  -> IN_USE | CANCELLED | EXPIRED | FORCE_CANCELLED
IN_USE    -> COMPLETED | OVERDUE
OVERDUE   -> COMPLETED
```

**「占用柜格」的集合 = {RESERVED, IN_USE, OVERDUE}**，这是后面所有冲突检测、并发控制、可用性查询的唯一判定依据。

## 3. 业务规则与异常处理规则

### 3.1 时间与参数基础规则

| 编号 | 规则 | 违反时返回 |
|---|---|---|
| BR-01 | 时间粒度固定为 30 分钟，`start_time`、`end_time` 的分钟数只能是 `00` 或 `30`，秒必须为 `00` | 400 `TIME_NOT_ALIGNED` |
| BR-02 | `end_time > start_time`，最短 1 个时段（30 分钟），最长 144 个时段（72 小时） | 400 `DURATION_OUT_OF_RANGE` |
| BR-03 | `start_time >= NOW() + 5 分钟`（不允许预约已经开始或即将开始的时间） | 400 `TIME_IN_PAST` |
| BR-04 | `start_time <= NOW() + 7 天`（最多提前 7 天预约） | 400 `BOOKING_WINDOW_EXCEEDED` |
| BR-05 | 预约时间必须落在寄存点的营业时间内（默认 08:00 ~ 22:00） | 400 `OUT_OF_BUSINESS_HOURS` |
| BR-06 | 行李尺寸为枚举 `SMALL / MEDIUM / LARGE`，其他值非法 | 400 `VALIDATION_ERROR` |
| BR-07 | 本期 `luggage_count` 固定为 1（一个订单占一个柜格、放一件行李）；>1 返回 400，多件合柜列为【未实现】 | 400 `MULTI_LUGGAGE_NOT_SUPPORTED` |

### 3.2 资源与尺寸规则

| 编号 | 规则 | 违反时返回 |
|---|---|---|
| BR-08 | 行李尺寸等级必须 `<=` 柜格规格的尺寸等级（`SMALL < MEDIUM < LARGE`）。允许「大柜放小行李」，禁止「小柜放大行李」 | 400 `SIZE_NOT_MATCH` |
| BR-09 | 柜格 `physical_status != AVAILABLE`（维护中/停用）时不可预约 | 409 `CABINET_NOT_AVAILABLE` |
| BR-10 | 柜格所属柜体 `status != NORMAL` 时，其下所有柜格不可预约 | 409 `CABINET_NOT_AVAILABLE` |
| BR-11 | 柜格所属寄存点 `status != OPEN` 时不可预约 | 409 `POINT_CLOSED` |
| BR-12 | 柜格规格 `is_active = 0` 时不可用于新预约（历史订单不受影响） | 409 `CABINET_TYPE_DISABLED` |

### 3.3 时段冲突规则（核心）

| 编号 | 规则 | 违反时返回 |
|---|---|---|
| BR-13 | **同一柜格的两个「占用类」订单时间区间不允许重叠**。判定条件（左闭右开）：`EXISTS(订单 o WHERE o.cabinet_id=? AND o.status IN ('RESERVED','IN_USE','OVERDUE') AND o.start_time < :new_end AND o.end_time > :new_start)` | 409 `CABINET_TIME_CONFLICT` |
| BR-14 | 相邻不重叠的预约**必须允许**（例如 10:00-11:00 与 11:00-12:00 可共存），这是关键边界用例 | —— |
| BR-15 | 用户对**同一柜格同一时间段**的第二次预约，属于 BR-13 冲突，返回 409 | 409 `CABINET_TIME_CONFLICT` |

### 3.4 幂等与重复提交规则

| 编号 | 规则 | 违反时返回 |
|---|---|---|
| BR-16 | 创建预约必须携带 `idempotency_key`（客户端生成的 UUID，长度 8~64）。同一用户 + 同一 key 只允许产生一个订单，数据库层由唯一索引 `uk_user_idem(user_id, idempotency_key)` 保证 | 见下方处理约定 |
| BR-17 | 重复提交同一个 key 时，**返回第一次创建的订单**，HTTP `200`，响应体带 `"idempotent_replay": true`（首次为 `201`、`false`）。语义是幂等，而不是报错 | —— |
| BR-18 | `idempotency_key` 缺失或格式非法 | 400 `VALIDATION_ERROR` |

> BR-17 的返回语义是**待确认项**（可改为直接 409 `DUPLICATE_REQUEST`，更易断言但不符合幂等语义），见第 13 节。

### 3.5 取消 / 签到 / 取件规则

| 编号 | 规则 | 违反时返回 |
|---|---|---|
| BR-19 | 用户取消：订单必须为 `RESERVED`，且 `NOW() <= start_time - 30 分钟` | 409 `CANCEL_WINDOW_EXPIRED` / `ORDER_STATUS_NOT_ALLOWED` |
| BR-20 | 取消成功后必须释放柜格时段（该柜格该时段可被重新预约） | —— |
| BR-21 | 签到窗口：`start_time - 15 分钟 <= NOW() <= start_time + 30 分钟`，订单状态必须为 `RESERVED` | 409 `CHECKIN_WINDOW_INVALID` |
| BR-22 | `checkin_deadline = start_time + 30 分钟`（存入宽限期，可通过配置项调整） | —— |
| BR-23 | 取件：订单状态必须为 `IN_USE` 或 `OVERDUE` | 409 `ORDER_STATUS_NOT_ALLOWED` |
| BR-24 | 取件在 `end_time` 之前完成时，柜格剩余时段**立即释放**（不等到 `end_time`） | —— |

### 3.6 权限规则

| 编号 | 规则 | 违反时返回 |
|---|---|---|
| BR-25 | 未登录访问需登录接口 -> 401 `AUTH_TOKEN_MISSING` / `AUTH_TOKEN_INVALID` | 401 |
| BR-26 | 普通用户访问 `/admin/**` -> 403 `AUTH_FORBIDDEN` | 403 |
| BR-27 | 普通用户访问他人订单（`GET /reservations/{order_no}`、取消、签到）-> 403 `AUTH_FORBIDDEN`（不返回 404，避免泄露订单存在性；此为安全设计取舍） | 403 |
| BR-28 | 用户 `status = DISABLED` 时，登录与所有带 token 的请求 -> 403 `USER_DISABLED` | 403 |
| BR-29 | 登出后，旧 token 必须立即失效（通过 `users.token_version` 自增实现） | 401 `AUTH_TOKEN_INVALID` |

### 3.7 数据一致性规则

| 编号 | 规则 |
|---|---|
| BR-30 | 「创建预约」必须在**单个数据库事务**内完成：写订单 + 写时段占用记录 + 写状态日志，全部成功或全部回滚 |
| BR-31 | 「取消 / 超时释放 / 取件」必须在**单个数据库事务**内完成：改订单状态 + 释放时段占用 + 写状态日志 |
| BR-32 | 任何一次「创建预约」失败，数据库中都不得残留订单、时段占用记录或错误的柜格状态 |
| BR-33 | 订单状态变更必须留下 `reservation_status_logs` 审计记录（含操作人类型、操作人 ID、变更前后状态） |
| BR-34 | 终态订单（`COMPLETED/CANCELLED/EXPIRED/FORCE_CANCELLED`）不允许再被修改状态 |
| BR-35 | 系统内的「当前时间」一律以**数据库 `NOW()`** 为准，避免应用服务器与数据库时钟不一致导致边界判定抖动 |

### 3.8 超时释放任务规则

| 编号 | 规则 | 违反/异常时行为 |
|---|---|---|
| BR-36 | 任务处理对象：`status='RESERVED' AND checkin_deadline <= NOW()` | —— |
| BR-37 | **任务必须可重复执行而结果一致**：第二次执行时这些订单已不是 `RESERVED`，条件不再命中，`affected_count = 0` | —— |
| BR-38 | 任务对每个订单使用条件更新 `WHERE id=? AND status='RESERVED'`，用 `rowcount` 判断是否真正处理，杜绝并发重复处理 | —— |
| BR-39 | 任务不得处理 `IN_USE` / `OVERDUE` 的订单（行李在柜内，不能自动释放） | —— |
| BR-40 | 每次任务执行必须写入 `job_execution_logs`（扫描数、实际影响数、成功/失败、耗时） | 单条订单失败时记录错误并继续处理其它订单 |
| BR-41 | 本期任务调度运行在**单进程**内（`uvicorn --workers 1`）；多实例分布式调度列为【未实现】 | —— |

### 3.9 统一错误响应格式与业务错误码

所有业务异常返回：

```json
{
  "code": "CABINET_TIME_CONFLICT",
  "message": "该柜格在所选时间段已被预约，请重新选择",
  "detail": { "cabinet_id": 12, "start_time": "2026-10-20 10:00:00", "end_time": "2026-10-20 12:00:00" },
  "request_id": "5f3c1a2b-..."
}
```

| 错误码 | HTTP | 含义 |
|---|---|---|
| `VALIDATION_ERROR` | 400 | 参数格式/枚举非法 |
| `TIME_NOT_ALIGNED` | 400 | 时间未按 30 分钟对齐 |
| `DURATION_OUT_OF_RANGE` | 400 | 时长超出范围 |
| `TIME_IN_PAST` | 400 | 开始时间过早 |
| `BOOKING_WINDOW_EXCEEDED` | 400 | 超出可预约窗口 |
| `OUT_OF_BUSINESS_HOURS` | 400 | 超出营业时间 |
| `SIZE_NOT_MATCH` | 400 | 行李尺寸与柜格不匹配 |
| `MULTI_LUGGAGE_NOT_SUPPORTED` | 400 | 暂不支持多件行李合柜 |
| `AUTH_TOKEN_MISSING` / `AUTH_TOKEN_INVALID` / `AUTH_TOKEN_EXPIRED` | 401 | 认证失败 |
| `AUTH_INVALID_CREDENTIALS` | 401 | 用户名或密码错误 |
| `AUTH_FORBIDDEN` | 403 | 越权访问 |
| `USER_DISABLED` | 403 | 账号被禁用 |
| `RESOURCE_NOT_FOUND` | 404 | 资源不存在（柜格/订单/寄存点） |
| `USERNAME_EXISTS` | 409 | 用户名已被占用 |
| `CABINET_TIME_CONFLICT` | 409 | 柜格时段冲突（含并发冲突兜底） |
| `CABINET_NOT_AVAILABLE` | 409 | 柜格维护中/停用/所属柜体或寄存点不可用 |
| `CABINET_TYPE_DISABLED` | 409 | 柜格规格已停用 |
| `ORDER_STATUS_NOT_ALLOWED` | 409 | 当前订单状态不允许该操作 |
| `CANCEL_WINDOW_EXPIRED` | 409 | 已超过可取消时间 |
| `CHECKIN_WINDOW_INVALID` | 409 | 不在签到时间窗口内 |
| `DB_CONSTRAINT_CONFLICT` | 409 | 数据库唯一约束兜底拦截（并发竞争的最终防线） |
| `LOCK_TIMEOUT` | 503 | 获取柜格行锁超时（高并发下重试建议） |
| `INTERNAL_ERROR` | 500 | 未预期异常 |

> 使用 `request_id`（中间件生成）串联日志，便于缺陷复现时定位。

## 4. 系统架构与技术选型理由

### 4.1 整体架构（单机三层，非微服务）

```
┌──────────────────────────────────────────────────────────┐
│  浏览器（HTML + CSS + 原生 JS fetch，服务端静态托管）      │
└───────────────┬──────────────────────────────────────────┘
                │ HTTP / JSON（JWT Bearer）
┌───────────────▼──────────────────────────────────────────┐
│  FastAPI 应用（单进程 uvicorn）                            │
│  ├─ api/v1/*        路由层：参数校验、鉴权依赖、响应组装    │
│  ├─ services/*      业务层：规则校验、状态机、事务边界      │
│  ├─ repositories/*  数据访问层：SQLAlchemy Session 操作     │
│  ├─ jobs/*          APScheduler 定时任务（超时释放/逾期标记）│
│  └─ core/*          配置、JWT、日志、统一异常处理、request_id│
└───────────────┬──────────────────────────────────────────┘
                │ SQLAlchemy ORM + InnoDB 事务/行锁
┌───────────────▼──────────────────────────────────────────┐
│  MySQL 8.0（InnoDB, utf8mb4, REPEATABLE READ）            │
└──────────────────────────────────────────────────────────┘
```

### 4.2 关键选型理由

| 选型 | 理由 |
|---|---|
| **FastAPI** | 自动生成 OpenAPI/Swagger 文档，便于接口测试时快速核对参数；Pydantic 原生参数校验，能直接产出可断言的 422/400 响应；异步能力足够支撑并发测试 |
| **MySQL 而非 SQLite** | 本项目最核心技术点是**并发预约**，需要真实的 InnoDB 行锁、间隙锁、事务隔离级别来验证。SQLite 的写锁机制与 MySQL 差异大，无法作为并发测试的有效载体 |
| **SQLAlchemy** | 显式控制 `Session` 与事务边界，`with_for_update()` 直接生成 `SELECT ... FOR UPDATE`，便于在面试中讲清「锁是在哪一行、哪个事务上加的」 |
| **JWT + token_version** | 无状态鉴权便于接口测试；`token_version` 让「登出后 token 立即失效」成为**可验证**行为，而不是前端假登出 |
| **APScheduler 内嵌** | 单机单进程场景下无需 Celery/Redis/消息队列；任务频繁执行且需要「重复执行幂等」的测试点，内嵌调度器最易观测和手动触发 |
| **原生 HTML/CSS/JS** | 前端不是本项目的测试重点，但必须有真实可用的交互（表单提交、按钮禁用、错误提示、列表刷新）来支撑 Selenium UI 自动化；避免引入前端构建链 |
| **明确不引入** | Redis、消息队列、微服务、Docker 集群、Nginx 反向代理 —— 增加部署成本却对测试目标（业务规则、并发、一致性）无实质增益 |

### 4.3 部署形态（本地开发/演示）

- 后端：`uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1`（**必须单 worker**，原因见 BR-41）
- 前端：由 FastAPI `StaticFiles` 挂载在 `/`，与接口同源，避免 CORS 复杂度（同时保留 CORS 中间件便于 Postman/JMeter 直连）
- 数据库：本机 MySQL 8 实例，库名 `luggage_locker`，字符集 `utf8mb4`，时区 `+08:00`
- 时间约定：数据库 `DATETIME` 存储北京时间（无时区），接口输入输出统一为 `YYYY-MM-DD HH:mm:ss`

## 5. 数据库表设计

### 5.0 通用约定

- 引擎 `InnoDB`，字符集 `utf8mb4` / `utf8mb4_general_ci`
- 主键统一 `id BIGINT UNSIGNED AUTO_INCREMENT`
- 时间字段统一 `DATETIME`（精确到秒）
- `created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`，`updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`
- 金额统一 `DECIMAL(10,2)`
- **不使用物理删除**：寄存点/柜体/柜格/规格/用户均通过状态字段停用；订单永不删除
- 外键统一 `ON DELETE RESTRICT ON UPDATE RESTRICT`（`reservation_slots` 除外，见 5.7）
- **快照原则**：历史订单中需要保留下单时的信息（寄存点名、柜格编号、规格、单价），但只在**订单表**做冗余快照；业务主表之间严格第三范式，避免多处数据可能不一致

> **重要设计说明：柜格状态只存一份真相**
> 数据库里 `cabinets.physical_status` **只表达运维维度**（可用/维护中/停用）。
> UI 上要求区分的「可用 / 已预约 / 使用中 / 维护中」是**派生状态**，由服务层按指定时间段动态计算：
>
> | 展示状态 | 计算规则 |
> |---|---|
> | 维护中 | `physical_status = MAINTENANCE`（或所属柜体/寄存点不可用则为「不可用」） |
> | 停用 | `physical_status = DISABLED` |
> | 使用中 | 存在该柜格 `status IN ('IN_USE','OVERDUE')` 的订单 |
> | 已预约 | 在查询时间段内存在 `status='RESERVED'` 的重叠订单 |
> | 可用 | 以上都不满足 |
>
> 这样做的好处：**不存在「订单已取消但柜格还显示已预约」这类双写不一致**，因为柜格占用状态完全是订单的派生结果。这一点也是测试用例设计的重要依据。

### 5.7 reservation_slots —— 预约时段占用（防超卖的数据库兜底层）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | PK | |
| reservation_id | BIGINT UNSIGNED | NOT NULL, FK→reservations.id **ON DELETE CASCADE** | |
| cabinet_id | BIGINT UNSIGNED | NOT NULL, FK→cabinets.id | |
| slot_start | DATETIME | NOT NULL | 该占用的时段起点（30 分钟对齐） |

索引：**`uk_slots_cabinet_slot(cabinet_id, slot_start)`** —— 这一条唯一索引是**物理层面的防超卖保险丝**：即使应用层逻辑出现漏洞，同一柜格同一时段也只能存在一条占用记录。
`idx_slots_reservation(reservation_id)`

生命周期：

- 创建预约成功时，把 `[start, end)` 按 30 分钟拆成 N 条记录插入（同一事务）；
- 订单进入终态（`CANCELLED/EXPIRED/COMPLETED/FORCE_CANCELLED`）时，**删除该订单的全部 slot 记录**（同一事务），从而释放资源；
- 因 `slot_minutes` 固定为 30，离散化可行；若未来粒度可变，本表需要同步调整（列为【未实现】的可扩展点）。

- 统一前缀 `/api/v1`

## 8. 并发预约的实现思路

### 8.1 要解决的问题

并发预约的典型缺陷是 **TOCTOU（检查后使用之间的时间差）**：

```
线程 A: 查询柜格 12 在 10:00-12:00 是否有冲突  -> 无冲突
线程 B: 查询柜格 12 在 10:00-12:00 是否有冲突  -> 无冲突
线程 A: 插入订单 A
线程 B: 插入订单 B          <-- 同一柜格同一时段两张有效订单，超卖
```

只要"检查"和"写入"不是原子的，就一定会出现这个问题。仅靠应用层 `if 无冲突: 插入` 无法解决。

### 8.2 四层防线（从外到内）

| 层 | 机制 | 拦截的问题 | 是否本期实现 |
|---|---|---|---|
| L1 应用层 | 请求幂等键 `idempotency_key` | 用户重复点击、网络重试导致的**同一请求**重复 | ✅ |
| L2 事务层 | 对柜格行 `SELECT ... FOR UPDATE` 悲观锁，串行化同一柜格的创建 | **不同请求**抢占同一柜格 | ✅ |
| L3 事务层 | 事务内重新做时段冲突查询（左闭右开区间判定） | 业务语义冲突 | ✅ |
| L4 数据库层 | `uk_slots_cabinet_slot(cabinet_id, slot_start)` 唯一索引 | 上述逻辑的任何漏网之鱼（最终保险丝） | ✅ |

### 8.3 创建预约的事务流程（设计示意，非最终代码）

```
BEGIN;

-- 0) 幂等预检（快速路径，命中则直接返回既有订单，不开事务做后续操作）

-- 1) 锁定柜格行 —— 这是整个方案的串行化点
SELECT c.id, c.physical_status, c.type_id, g.status AS group_status, p.status AS point_status
FROM cabinets c
JOIN cabinet_groups g ON c.group_id = g.id
JOIN storage_points p ON g.point_id = p.id
WHERE c.id = :cabinet_id
FOR UPDATE;                      -- 锁住 cabinets 这一行，直到事务结束

-- 2) 业务规则校验（在持有锁的前提下做，结果不会被其他事务改变）
--    BR-09/10/11/12：柜格、柜体、寄存点、规格状态校验
--    BR-08：行李尺寸 <= 规格尺寸等级
--    BR-01~05：时间对齐、时长、提前量、营业时间

-- 3) 时段冲突检测（占用类状态集合）
SELECT id, order_no,
       (SELECT COUNT(*) FROM reservations
        WHERE cabinet_id = :cabinet_id
          AND status IN ('RESERVED','IN_USE','OVERDUE')
          AND start_time < :new_end
          AND end_time   > :new_start) AS conflict_cnt;

-- 冲突 -> ROLLBACK，返回 409 CABINET_TIME_CONFLICT

-- 4) 写订单
INSERT INTO reservations (...) VALUES (...);

-- 5) 写时段占用（按 30 分钟离散，N 条）
INSERT INTO reservation_slots (reservation_id, cabinet_id, slot_start) VALUES (...), (...), ...;
--    若此处抛 IntegrityError（唯一键 uk_slots_cabinet_slot 冲突）
--      -> ROLLBACK，返回 409 CABINET_TIME_CONFLICT（错误码 DB_CONSTRAINT_CONFLICT 亦可）

-- 6) 写状态日志
INSERT INTO reservation_status_logs (...) VALUES (NULL, 'RESERVED', 'USER', :user_id, '创建预约');

COMMIT;   -- 提交后才释放柜格行锁
```

### 8.4 为什么选悲观锁而不是别的方案

| 方案 | 说明 | 本项目取舍 |
|---|---|---|
| **悲观锁（柜格行 `FOR UPDATE`）** | 锁的是**柜格主记录**这一行，而不是"还不存在的订单"，因此**必然能锁住**（柜格行一定存在）。同一柜格的所有创建请求被严格串行化，逻辑最简单也最可靠 | ✅ **采用** |
| 乐观锁（version 字段） | 需要柜格上维护"时段占用版本号"，冲突时需要重试；在"不同用户抢同一柜格"这种高冲突场景下重试率极高 | ❌ 不采用 |
| 仅靠 `reservation_slots` 唯一索引 | 可行，但把业务语义完全压到 DB 层，冲突时只能拿到 `IntegrityError`，无法区分"是时段冲突还是其他唯一键冲突"，错误信息不友好；且一旦粒度变化就要重建表 | ⚠️ 作为 L4 兜底，不作为唯一机制 |
| Redis 分布式锁 | 需要额外中间件，且仍不能替代 DB 约束 | ❌ 不采用 |
| 数据库隔离级别（SERIALIZABLE） | 全局代价大，且死锁概率显著上升 | ❌ 不采用 |

**关于 `SELECT ... FOR UPDATE` 锁不到记录的问题**：本项目故意选择锁 `cabinets` 表的**已存在行**，而不是锁 `reservations` 中不存在的"冲突区间"，从根上绕开了"间隙锁/幻读"带来的不确定性。这样即使把隔离级别调成 `READ COMMITTED`，正确性依然成立——**正确性不依赖隔离级别**，这一点在面试讲解时是很强的加分项。

### 8.5 死锁与锁等待

- 单次预约只锁**一个**柜格行，因此天然不存在"多把锁加锁顺序不一致"导致的死锁；
- 未来若支持"一个订单占多个柜格"，必须按 `cabinet_id` **升序**加锁，否则会死锁（列为【未实现】的可扩展约束）；
- `innodb_lock_wait_timeout` 设为 5 秒；锁等待超时统一转换为 `503 LOCK_TIMEOUT`，由调用方决定是否重试，**不返回 500**；
- 事务内不做任何外部调用、不做耗时计算，把锁持有时间压到最短（写操作全在锁内，但逻辑只有几条 SQL）。

### 8.6 其他会改变「柜格时段占用」的操作必须用同一把锁

取消、超时释放、取件，都会**删除 `reservation_slots` 记录**，从而改变该柜格的占用集合。如果它们不加同一把柜格行锁，就可能出现"删除 + 插入"交错的竞态。

因此规定：**以下操作必须在事务内先对相关 `cabinet_id` 执行 `SELECT ... FOR UPDATE`，加锁顺序按 `cabinet_id` 升序**：

| 操作 | 加锁对象 | 原因 |
|---|---|---|
| 创建预约 | 目标柜格 | 检查冲突 + 插入占用 |
| 用户取消 | 订单的柜格 | 删除占用记录 |
| 超时释放 | 每条订单的柜格 | 删除占用记录 |
| 取件完成 | 订单的柜格 | 删除剩余时段占用（BR-24） |

### 8.7 如何真实验证（与第 10 节的工具对应）

1. **JMeter 真实并发**：线程组 N=50/100，添加 **Synchronizing Timer**（集合点），所有线程在同一时刻发起 `POST /reservations`，且**使用 N 个不同用户的 token、目标同一 `cabinet_id` 与同一时间段**；
   - 断言：`HTTP 201` 的响应数**恰好为 1**；其余为 `409`；
   - 数据库校验：`SELECT COUNT(*) FROM reservations WHERE cabinet_id=? AND status IN ('RESERVED','IN_USE','OVERDUE') AND start_time<? AND end_time>?` 结果**必须为 1**；`reservation_slots` 中该柜格该时段记录数与时段数一致，无重复 `slot_start`。
2. **pytest 真并发**：`ThreadPoolExecutor` + `threading.Barrier(N)` 让 N 个线程同一时刻发请求（`Barrier` 是"真实并发"的关键，普通 `for` 循环只是顺序请求，**不能**称为并发测试）；
3. **对照实验（用于面试讲解）**：临时移除柜格行锁（或移除 `reservation_slots` 唯一索引），重跑同一脚本，观察确实出现超卖，再恢复，形成"缺陷—修复—回归"的完整故事。

## 9. 预约超时释放机制的实现方案

### 9.1 触发方式（三种入口，共用同一个服务方法）

| 入口 | 触发方 | 用途 |
|---|---|---|
| APScheduler 定时任务 | 系统，每 60 秒（`release_job_interval_seconds`） | 生产行为 |
| `POST /admin/jobs/release-expired/run` | 管理员/测试人员 | **手动触发，用于验证重复执行幂等** |
| CLI 脚本 `python -m app.jobs.release_expired` | 开发/测试 | 不启服务也能跑，便于数据构造 |

### 9.2 处理逻辑（两个独立任务）

**任务一：`release_expired_reservations`（超时未签到释放）**

```
BEGIN
SELECT NOW() INTO :now;                       -- 时间以数据库为准（BR-35）

-- 1) 先查出候选订单 ID（只查 ID，快照扫描，不长时间持有行锁）
SELECT id, cabinet_id FROM reservations
WHERE status = 'RESERVED'
  AND checkin_deadline <= :now
ORDER BY id
LIMIT 500;                                    -- 分批，避免一次锁太多行

-- 2) 对每个候选订单独立小事务处理
FOR EACH order_id:
  BEGIN
    SELECT cabinet_id FROM reservations WHERE id = :order_id;
    SELECT id FROM cabinets WHERE id = :cabinet_id FOR UPDATE;   -- 与创建预约同一把锁

    -- 3) 条件更新：幂等的核心。第二次执行 rowcount = 0
    UPDATE reservations
    SET status = 'EXPIRED', cancelled_at = :now, cancel_reason = '超时未签到自动释放'
    WHERE id = :order_id AND status = 'RESERVED';

    IF rowcount = 1:
        DELETE FROM reservation_slots WHERE reservation_id = :order_id;   -- 释放时段
        INSERT INTO reservation_status_logs (reservation_id, from_status, to_status,
                operator_type, remark)
        VALUES (:order_id, 'RESERVED', 'EXPIRED', 'SYSTEM', '超时未签到自动释放');
        affected += 1;
    ELSE:
        -- 已被其他执行者处理，直接跳过
        skipped += 1;
  COMMIT
END FOR

INSERT INTO job_execution_logs (job_name, trigger_type, started_at, finished_at,
       scanned_count, affected_count, result)
VALUES ('release_expired_reservations', :trigger, ..., scanned, affected, 'SUCCESS');
```

**任务二：`mark_overdue_reservations`（到期末取件标记）**

```
UPDATE reservations
SET status = 'OVERDUE'
WHERE status = 'IN_USE' AND end_time < NOW();
-- 注意：不删除 reservation_slots，不释放柜格（行李仍在柜内）
-- 同样条件更新，重复执行 rowcount = 0，天然幂等
```

### 9.3 幂等性保证的四重设计

1. **条件更新**：`WHERE id=? AND status='RESERVED'`，状态是终态时不再命中，`rowcount=0`；
2. **柜格行锁**：与创建预约使用同一把锁，保证"释放"和"新预约"不会交错；
3. **单订单小事务**：一条订单失败不影响其他订单，任务整体结果可为 `PARTIAL`；
4. **执行日志**：连续两次手动触发，`affected_count` 第一次 N、第二次 0，这是**可被自动化断言**的验收证据。

### 9.4 边界处理

| 场景 | 处理 |
|---|---|
| 订单恰好落在边界（`checkin_deadline == NOW()`） | 使用 `<=`，即"到点即释放"，并在测试用例中明确该边界预期 |
| 候选订单在扫描与处理之间被用户签到 | 条件更新 `rowcount=0`，跳过，不影响用户签到 |
| 候选订单在扫描与处理之间被用户取消 | 同上，跳过 |
| 一个柜格同一时刻有多条待释放订单 | 单柜格串行处理；实际上同一柜格不会存在多条重叠的 `RESERVED` 订单（由 BR-13 保证） |
| 任务执行耗时超过 60 秒 | APScheduler 配置 `max_instances=1`，避免同一任务堆叠执行 |
| 多进程/多实例部署 | 【未实现】本期强制单 worker；文档中明确该限制，作为已知设计边界而非缺陷 |

### 9.5 与业务规则的呼应

- 释放后，BR-20 要求"该柜格该时段可被重新预约"——因为 `reservation_slots` 记录被删除、且订单已非占用类状态，`GET /cabinets/availability` 会自然地把这些时段算作可用；
- 释放后**不修改 `cabinets.physical_status`**，再次印证 5.5 节的"柜格状态单一真相"设计。

### 10.3 JMeter 测试计划设计

| 计划 | 线程组 | 参数 | 断言/校验 |
|---|---|---|---|
| **P-01 只读查询** | 查询寄存点 + Q5 可用性 | 梯度 50 / 100 / 200 线程，Ramp-up 10s，循环 20 次 | TPS、平均/90 分位响应时间、错误率；找出响应时间拐点 |
| **P-02 并发抢同一柜格** | N 个线程同时 `POST /reservations`，**指向同一 cabinet_id + 同一时间段**，配 Synchronizing Timer(N) | N=50、100、200；每个线程独立用户 token（用 CSV Data Set Config 读取 200 个用户的 token） | **断言 201 的数量 == 1**，其余全为 409；数据库校验占用订单数 == 1 |
| **P-03 并发抢多柜格** | 同上，但 `cabinet_id` 从一个 20 个柜格的池中随机取 | 200 线程 | 断言：每个柜格在其时段内成功订单数 == 1；总成功数 <= 20 |
| **P-04 重复提交** | 单用户用**同一个 `idempotency_key`** 并发提交 10 次 | 10 线程，集合点 | 断言：数据库订单数 == 1；接口返回 1 个 201 + 9 个 200(`idempotent_replay=true`)，或（若采用 409 语义）1 个 201 + 9 个 409 |
| **P-05 混合场景** | 70% 查询 + 20% 预约 + 10% 取消 | 100 线程，持续 5 分钟 | 稳定性、锁等待 (`LOCK_TIMEOUT`) 比例、无 500 |

> 每个计划都要在报告中同时给出**JMeter 聚合报告** 与 **数据库校验 SQL 结果**，这是本项目最能体现"测试负责人思维"的部分。
