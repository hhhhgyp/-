## 0. 文档约定

### 0.1 断言原则

一条用例通过 = **四类证据同时成立**，缺一不可：

1. HTTP 状态码正确；
2. 响应体 `code` 字段正确（业务错误码，**不比对中文文案**）；
3. 响应体关键字段正确（金额、状态、时段数、`can_*` 等）；
4. 数据库状态正确（订单 / 时段 / 状态日志）。

只断言"页面提示成功"或只看 HTTP 200 不算通过。

### 0.3 时间基准与写法

- 系统所有"当前时间"判定取**数据库 `NOW()`**（BR-35）。执行任何时间边界用例前先执行 `SELECT NOW();`，用例中的 `D0` 一律指**数据库当前日期**（`SELECT CURDATE();`），不是操作系统的日期。
- 用例写作 `D0+1 10:00`，表示"数据库当前日期 + 1 天的 10:00:00"。
- 需要精确边界的用例，用 SQL 现算（不要手填），统一取整规则：

```sql
-- 向上取整到下一个 30 分钟（用于 BR-03 下界、签到窗口）
SELECT DATE_ADD(
         DATE_FORMAT(DATE_ADD(NOW(), INTERVAL 5 MINUTE), '%Y-%m-%d %H:%i:00'),
         INTERVAL (30 - MINUTE(DATE_ADD(NOW(), INTERVAL 5 MINUTE)) % 30) % 30 MINUTE
       ) AS next_aligned;
```

- 时区必须是 `Asia/Shanghai`（`SELECT @@global.time_zone, @@session.time_zone, NOW();`）。数据库存的是 **naive DATETIME（北京时间）**，如果部署机或 MySQL 时区不同，BR-03/BR-05 会整体偏移——这本身就是一条环境准入检查。

## 1. 测试需求分析

### 1.1 被测系统实际组成

| 层 | 实现 |
|---|---|
| 接口 | 36 个操作（用户端 15、管理端 17、认证 4），OpenAPI 可枚举 |
| 业务 | 预约创建 / 查询 / 取消 / 签到 / 取件；柜格可用性；超时释放；逾期标记 |
| 数据 | 10 张表；核心是 `reservations` + `reservation_slots` + `reservation_status_logs` |
| 并发控制 | 柜格行 `SELECT … FOR UPDATE` + `uk_slots_cabinet_slot` 唯一索引 |
| 调度 | 进程内 APScheduler，2 个任务共用 1 个间隔（默认 60 秒） |
| 前端 | 原生 HTML/CSS/JS，14 页；业务规则全部由后端计算（`can_*`） |

### 1.2 核心业务链路

```
查询可用柜格 Q5/Q6
      │  尺寸过滤、派生状态
      ▼
创建预约 R1  ──► RESERVED ──► 签到 R5 ──► IN_USE ──► 取件 R6 ──► COMPLETED
      │                │                      │
      │                │                      └─► 逾期任务 ──► OVERDUE ──► 取件 R6
      │                ├─► 取消 R4 ──► CANCELLED
      │                └─► 超时未签到 ──► EXPIRED
      └─► 管理端强制取消 M11 ──► FORCE_CANCELLED

每条状态变更：订单状态 + 时段占用（增/删）+ 审计日志，同一事务
```

### 1.4 测试范围

**范围内**

- 认证：注册、登录、登出、`/me`、JWT 失效、账号禁用。
- 只读查询：Q1/Q2/Q3/Q4/Q5/Q6/Q7/Q8，含分页、筛选、派生状态、尺寸过滤。
- 预约：BR-01~BR-18 全部规则；金额、时段、快照、审计。
- 生命周期：取消、签到、取件、超时释放、逾期标记、调度器。
- 权限：401/403、订单归属、管理端路由守卫、前端页面守卫。
- 管理端：M1~M15 + M6b；批量建柜的"全有或全无"；统计口径；配置边界。
- 数据一致性：订单 ↔ 时段 ↔ 日志 ↔ 主数据。
- 并发：下单、取消、签到 vs 释放、维护 vs 下单。
- 性能基线：Q5 只读压测。

**范围外（有明确理由）**

| 项 | 理由 |
|---|---|
| 支付、退款 | 未实现，`pay_status` 恒为 `UNPAID` |
| 多件行李 / 合柜 | BR-07 固定 1 件，>1 直接 400 |
| 短信/推送/邮件 | 未实现 |
| 限流、验证码、密码找回 | 未实现（C14 明确不做） |
| 分布式多实例调度 | BR-41 明确单进程 |
| 渗透测试、加密算法评审 | 超出本项目范围；仅做基本越权与口令存储检查 |
| 72 小时以上长稳 | 单机演示项目，按 2 小时稳定性观察代替 |

### 1.5 由风险推导出的四条策略

1. **凡是"两个以上对象同时变化"的逻辑，一律双证据**：接口响应 + 立即查库，不信任任一单独来源。
2. **凡是时间规则，一律用数据库算边界值**，禁止手填 `2026-10-20` 这类固定日期（会随时间失效）。
3. **并发用例必须"真并发"**：多线程/多进程同时发起，禁止循环顺序调用冒充并发；判定标准是"数据库只有一份正确结果"，不是"接口没报错"。
4. **错误码优先级按文档固定顺序断言**：同一请求故意违反多条规则时，只接受设计规定的那个错误码。

### 2.7 分层策略

```
        ┌──────────────┐
        │ UI 冒烟 (4)  │  ← 只验证"能走通、守卫有效"
        ├──────────────┤
        │ 并发/性能 (5) │  ← 只在主干稳定后执行
        ├──────────────┤
        │ 数据一致性(4) │  ← 每轮必跑，纯 SQL
        ├──────────────┤
        │ 业务规则 (110)│  ← 主体，接口级
        └──────────────┘
```

## 5. 数据库校验方法

### 5.1 原则

1. **接口响应用于定位，数据库用于定性**。响应说"已取消"不算数，`reservation_slots` 里还有行就是没取消。
2. **每条用例执行前后各取一次基线**（相关表的行数），用于证明"失败请求无残留"。
3. **只用只读 SQL 做校验**，不用 `UPDATE` 修数据来"让用例通过"；构造场景的 SQL 必须在用例中显式写明，并在结束后恢复。
4. **时间比较一律用 `NOW()`**，不比较应用侧时间字符串。

### 5.2 必查表与字段

| 表 | 必查字段 | 校验目的 |
|---|---|---|
| `reservations` | `order_no`、`user_id`、`cabinet_id`、`point_id`、`cabinet_type_id`、`start_time`、`end_time`、`slot_count`、`luggage_size`、`luggage_count`、`unit_price`、`amount`、`status`、`idempotency_key`、`checkin_deadline`、`checked_in_at`、`completed_at`、`cancelled_at`、`cancel_reason` | 订单主体、金额、状态、时间 |
| `reservation_slots` | `reservation_id`、`cabinet_id`、`slot_start` | 时段占用是否与订单一致、是否有唯一冲突 |
| `reservation_status_logs` | `reservation_id`、`from_status`、`to_status`、`operator_type`、`operator_id`、`created_at` | 状态迁移是否留痕、操作人是否正确 |
| `job_execution_logs` | `job_name`、`trigger_type`、`scanned_count`、`affected_count`、`failed_count`、`released_slot_count`、`result`、`started_at`、`finished_at` | 任务是否执行、结果是否自洽 |
| `cabinets` | `physical_status`、`group_id`、`type_id`、`code` | 物理状态与派生状态 |

| 从 | 到 | 触发 |
|---|---|---|
| — | `RESERVED` | R1 |

### 5.4 数据不变量清单（全部返回空集才算通过）

**C-01 占用类订单的时段数 = slot_count**

```sql
SELECT r.order_no, r.slot_count, COUNT(s.id) AS actual
FROM reservations r
LEFT JOIN reservation_slots s ON s.reservation_id = r.id
WHERE r.status IN ('RESERVED','IN_USE','OVERDUE')
GROUP BY r.id, r.order_no, r.slot_count
HAVING actual <> r.slot_count;
```

**C-02 终态订单不得残留时段**

```sql
SELECT r.order_no, r.status, COUNT(s.id) AS slots
FROM reservations r
JOIN reservation_slots s ON s.reservation_id = r.id
WHERE r.status IN ('COMPLETED','CANCELLED','EXPIRED','FORCE_CANCELLED')
GROUP BY r.id, r.order_no, r.status;
```

**C-03 时段唯一索引存在且无重复**

```sql
SHOW INDEX FROM reservation_slots WHERE Key_name = 'uk_slots_cabinet_slot';
SELECT cabinet_id, slot_start, COUNT(*) c
FROM reservation_slots GROUP BY cabinet_id, slot_start HAVING c > 1;
```

**C-04 占用类订单之间无重叠（应用层之外的最终复核）**

```sql
SELECT a.order_no AS order_a, b.order_no AS order_b, a.cabinet_id
FROM reservations a
JOIN reservations b
  ON a.cabinet_id = b.cabinet_id AND a.id < b.id
 AND a.status IN ('RESERVED','IN_USE','OVERDUE')
 AND b.status IN ('RESERVED','IN_USE','OVERDUE')
 AND a.start_time < b.end_time
 AND b.start_time < a.end_time;
```

**C-05 订单状态 = 最后一条审计日志的 to_status**

```sql
SELECT r.order_no, r.status, l.to_status, l.created_at
FROM reservations r
JOIN reservation_status_logs l
  ON l.id = (SELECT MAX(id) FROM reservation_status_logs WHERE reservation_id = r.id)
WHERE r.status <> l.to_status;
```

**C-06 每张订单至少一条审计日志，且首条 from_status 为 NULL**

```sql
SELECT r.order_no FROM reservations r
LEFT JOIN reservation_status_logs l ON l.reservation_id = r.id
WHERE l.id IS NULL;

SELECT r.order_no, l.from_status, l.to_status
FROM reservations r JOIN reservation_status_logs l ON l.reservation_id = r.id
WHERE l.id = (SELECT MIN(id) FROM reservation_status_logs WHERE reservation_id = r.id)
  AND (l.from_status IS NOT NULL OR l.to_status <> 'RESERVED');
```

**C-07 金额 = 单价 × 时段数（两位小数）**

```sql
SELECT order_no, unit_price, slot_count, amount,
       ROUND(unit_price * slot_count, 2) AS expected
FROM reservations
WHERE amount <> ROUND(unit_price * slot_count, 2);
```

**C-08 签到截止 = start_time + 30 分钟（默认配置下）**

```sql
SELECT order_no, start_time, checkin_deadline
FROM reservations
WHERE checkin_deadline <> DATE_ADD(start_time, INTERVAL 30 MINUTE);
```

**C-09 订单的寄存点 / 规格与柜格实际归属一致**

```sql
SELECT r.order_no, r.point_id, g.point_id AS cabinet_point, r.cabinet_type_id, c.type_id
FROM reservations r
JOIN cabinets c ON c.id = r.cabinet_id
JOIN cabinet_groups g ON g.id = c.group_id
WHERE r.point_id <> g.point_id OR r.cabinet_type_id <> c.type_id;
```

**C-10 时段起点与订单窗口匹配（30 分钟粒度）**

```sql
SELECT r.order_no, MIN(s.slot_start) AS first_slot,
       r.start_time,
       MAX(s.slot_start) AS last_slot,
       DATE_SUB(r.end_time, INTERVAL 30 MINUTE) AS expected_last
FROM reservations r
JOIN reservation_slots s ON s.reservation_id = r.id
WHERE r.status IN ('RESERVED','IN_USE','OVERDUE')
GROUP BY r.id, r.order_no, r.start_time, r.end_time
HAVING first_slot <> r.start_time OR last_slot <> expected_last;
```

**C-11 任务日志自洽**

```sql
SELECT id, job_name, result, scanned_count, affected_count, failed_count, skipped_count
FROM job_execution_logs
WHERE (failed_count = 0 AND result <> 'SUCCESS')
   OR (failed_count > 0 AND (affected_count > 0 OR skipped_count > 0) AND result <> 'PARTIAL')
   OR (failed_count > 0 AND affected_count = 0 AND skipped_count = 0 AND result <> 'FAILED')
   OR finished_at < started_at;
```

**C-12 口令不得明文存储**

```sql
SELECT username, LEFT(password_hash, 4) AS prefix
FROM users
WHERE password_hash NOT LIKE '$2%';   -- bcrypt 哈希以 $2a$/$2b$ 开头
```

**M12 占用率复算（与接口返回值三方核对）**

口径来自 `admin_service.stats_overview`：分母 = 柜格 `AVAILABLE` 且柜体 `NORMAL` 且寄存点 `OPEN` 且规格 `is_active`；分子 = 分母集合中，存在 `OVERDUE` 订单，或存在 `RESERVED/IN_USE` 且 `start_time <= NOW() < end_time` 的订单。

```sql
SELECT
  (SELECT COUNT(*) FROM cabinets c
     JOIN cabinet_groups g ON g.id = c.group_id
     JOIN storage_points p ON p.id = g.point_id
     JOIN cabinet_types t ON t.id = c.type_id
    WHERE c.physical_status='AVAILABLE' AND g.status='NORMAL'
      AND p.status='OPEN' AND t.is_active=1) AS denominator,
  (SELECT COUNT(*) FROM cabinets c
     JOIN cabinet_groups g ON g.id = c.group_id
     JOIN storage_points p ON p.id = g.point_id
     JOIN cabinet_types t ON t.id = c.type_id
    WHERE c.physical_status='AVAILABLE' AND g.status='NORMAL'
      AND p.status='OPEN' AND t.is_active=1
      AND EXISTS (SELECT 1 FROM reservations r
                   WHERE r.cabinet_id = c.id
                     AND (r.status='OVERDUE'
                          OR (r.status IN ('RESERVED','IN_USE')
                              AND r.start_time <= NOW() AND r.end_time > NOW())))) AS numerator;
```

> 注意：**未来时段的预约不计入分子**。用例设计时必须区分"占用率"（此刻）与"该时段是否可约"（Q5），两者口径不同，不是缺陷。

### 5.5 清理与基线恢复

```sql
-- 1) 删除测试订单（级联删除 slots；日志需先删）
DELETE l FROM reservation_status_logs l
JOIN reservations r ON r.id = l.reservation_id
WHERE r.idempotency_key LIKE 'tst-%';

DELETE FROM reservations WHERE idempotency_key LIKE 'tst-%';

-- 2) 删除测试主数据（按外键顺序）
DELETE c FROM cabinets c JOIN cabinet_groups g ON g.id = c.group_id
WHERE g.code LIKE 'TST-%';
DELETE FROM cabinet_groups WHERE code LIKE 'TST-%';
DELETE FROM storage_points WHERE code LIKE 'TST-SP%';
DELETE FROM cabinet_types WHERE code LIKE 'TST-%';

-- 3) 配置复位（按交付汇总 §4 的默认值逐项核对）
SELECT config_key, config_value FROM system_config ORDER BY config_key;

-- 4) 基线核对
SELECT
  (SELECT COUNT(*) FROM reservations)        AS reservations,
  (SELECT COUNT(*) FROM reservation_slots)   AS slots,
  (SELECT COUNT(*) FROM reservation_status_logs) AS logs,
  (SELECT COUNT(*) FROM storage_points)      AS points,
  (SELECT COUNT(*) FROM cabinet_groups)      AS groups_,
  (SELECT COUNT(*) FROM cabinets)            AS cabinets,
  (SELECT COUNT(*) FROM cabinet_types)       AS types;
```

允许的非零基线：`job_execution_logs`（历史执行记录）与 `users`（含演示账号）。

| **缺陷标题** | `[模块] 现象 + 条件`，一句话可检索，例如 `[预约] 签到窗口上界用应用时间导致晚 1 分钟仍可签到` |
| **缺陷编号** | `BUG-<轮次>-<序号>`，如 `BUG-R2-007` |
| **环境** | 提交号/工作区、OS、Python、MySQL、浏览器、服务启动参数（是否 `--no-scheduler`） |
| **前置条件** | 数据状态（订单号、柜格 ID、配置值）、账号、时间基准 `SELECT NOW()` 的结果 |
| **复现步骤** | 编号步骤，每步含**完整请求**（方法、URL、Header、Body）或页面操作路径；必须可被他人照做 |
| **预期结果** | 引用规则编号（BR-xx / 接口 x），写明状态码、`code`、关键字段、DB 期望 |
| **实际结果** | 真实响应（状态码 + body 摘要）+ 真实 DB 查询结果；不要写"不正确" |
| **严重程度** | S1~S4，见 §6.2 |
| **优先级** | P0~P3，见 §2.5 |
| **证据** | 响应截图/日志片段（含 `request_id`）、SQL 结果、必要时 HAR |
| **修复验证** | 修复后回归的用例 ID、验证时间、验证人、结论（通过/不通过） |
| **关联** | 关联用例、关联缺陷、是否阻塞发版 |

### 6.2 严重程度

| 级别 | 定义 | 例子 |
|---|---|---|
| S1 致命 | 数据错误/资金或资源损失/安全漏洞，主流程中断且无替代 | 超卖；他人可取消我的订单；订单已取消但时段未释放 |
| S2 严重 | 主要功能不可用或结果错误，但有临时绕行 | 签到窗口判定错误；金额算错；强制取消不释放时段 |
| S3 一般 | 次要功能错误、边界不符、错误码不正确 | 422 而非 400；分页 total 错；提示文案错 |
| S4 轻微 | 体验/文案/样式 | 按钮文案、对齐 |

### 6.3 示例（真实缺陷 D-03）

| 字段 | 内容 |
|---|---|
| 标题 | `[管理端] 普通用户访问管理页后无限重定向，denied=1 提示不可见` |
| 环境 | Windows 11 / Edge / 端口 8138 / 默认启动参数 |
| 前置 | `user01` 已登录；`/admin/index.html` 存在 |
| 步骤 | 1. 以 `user01` 登录；2. 地址栏访问 `http://127.0.0.1:8138/admin/index.html`；3. 观察地址栏与页面 |
| 预期 | 跳转 `/login.html?denied=1&redirect=%2Fadmin%2Findex.html`，显示"无权限"提示，页面稳定 |
| 实际 | 在 `/login.html` 与 `/admin/index.html` 之间反复跳转；`denied=1` 提示一闪而过；最终浏览器报 `ERR_TOO_MANY_REDIRECTS` |
| 严重程度 | S2 |
| 优先级 | P0 |
| 证据 | 浏览器历史记录中反复出现 `/login.html` 与 `/admin/index.html`（页面级跳转，不是 302）；`login.html` 中"已登录则跳 redirect"的分支 |
| 修复验证 | `login.html` 增加 `denied=1` 时不自动跳转；`common.js::requireAdmin` 用当前管理页路径生成 `redirect`。2026-10-20 Selenium Chrome 回归通过：`test_non_admin_guard_redirects_to_login_without_loop`、`test_non_admin_guard_on_orders_page_stays_denied`（8/8 UI 用例，50.29 s） |
| 关联 | TC-UI-02 |

### 6.4 流程

`新建 → 评审（定级/去重）→ 指派 → 修复 → 验证（同用例 + 回归集）→ 关闭`。
验证不通过则重新打开并附上新证据；不允许"口头确认已修复"。

## 8. 测试执行顺序

| 步 | 内容 | 目的 | 产出 |
|---|---|---|---|
| **0** | 环境与基线核查 | 排除"环境不对导致的假失败"：时区、种子、配置、36 个接口 | 基线快照（表行数、配置值） |
| **1** | 接口契约冒烟 | 确认路径/方法/鉴权/错误体格式；防止后续用例打在错误的 URL 上 | Postman 冒烟结果 |
| **2** | 认证与权限 | 先拿到稳定 token，并确认 401/403 边界；权限错了，后面的订单可能建到别人名下 | TC-AUTH、TC-AUTHZ 前半 |
| **3** | 只读查询 Q1~Q8 | 不写数据，先把"系统看到的资源"核对清楚；Q5 的派生状态是后续断言的基准 | TC-QRY 全量 |
| **4** | 创建预约单线程 | 规则最密集、最容易污染数据；先单线程把 BR-01~18 跑通，再谈并发 | TC-RES 全量 |
| **5** | 生命周期 | 依赖第 4 步产生的订单；验证状态机与时段释放 | TC-CAN、TC-CHK、TC-ORD |
| **6** | 管理端 | 会改主数据（柜格状态、规格、配置），放在用户端之后，避免污染 | TC-ADM 全量 |
| **7** | 数据一致性 SQL | 前 6 步写入了大量数据，此时跑不变量最有价值 | C-01~C-12 结果 |
| **8** | 真实并发 | 需要干净的柜格与稳定的主数据；放在功能轮之后，失败才好定位 | TC-CON-01~05 |
| **9** | 任务与调度器 | 需要构造过期/逾期订单，且要先关调度器造数、再开调度器验证 | TC-JOB 全量 |
| **10** | UI 冒烟 | 后端稳定后再验前端，避免把接口缺陷误判成页面缺陷 | TC-UI 全量 |
| **11** | 性能基线 | 最后执行；压测会产生大量日志，可能影响其它判定 | p95/吞吐/错误率 |
| **12** | 回归与报告 | 修复验证 + 准出判定 | 测试报告 |

顺序的三条硬约束：

1. **不跳步**：第 1 步失败还继续跑第 4 步，只会在错误的基线上产生大量噪音。
2. **管理端在用户端之后**：M5/M7/M9/M15 会改变柜格可用性、价格和业务参数，先跑会让第 4 步的预期全部失效。
3. **并发在功能之后**：并发用例的断言依赖"单线程下行为正确"这一前提，否则无法区分"并发缺陷"和"本来就是错的"。

## 9. 歧义与待确认（需产品/设计签字）

> 以下问题在实现中已有确定行为，但**业务语义**存在多种合理解释。测试按"当前实现"记录，不擅自判定为缺陷。

| 编号 | 问题 | 当前实现 | 影响 | 建议 |
|---|---|---|---|---|
| Q-01 | 同一 `idempotency_key` 但请求体不同（换柜格/换时段） | 返回**第一次**的订单，`200`，不校验 body 是否一致 | 客户端复用 key 会拿到"错误的单"，且看不出来 | 明确：要么校验 body 不一致返回 409，要么文档写死"key 即订单身份" |
| Q-02 | 同一 key 的**真并发**请求 | 可能有一个请求返回 `409 DB_CONSTRAINT_CONFLICT`（唯一索引兜底），而不是 `200` 重放 | 前端需同时处理 200/409 两种"重复提交" | 明确是否接受该竞态；若要求强一致需串行化或捕获后重查 |
| Q-03 | ADMIN 是否能以普通用户身份下单/取消 | 接口只校验登录，不校验角色，ADMIN 可以下单 | 运营账号产生业务订单，统计数据被污染 | 明确是否禁止；禁止则在 R1 增加角色校验 |
| Q-04 | 营业时间约束的是"存取时刻"还是"整个占用区间" | 约束 `start_time` / `end_time` 的**当日时刻**（否则 72 小时上限不成立） | 与设计文档原文措辞不同；若按区间解释，跨天预约全部非法 | 在需求文档中固化"时刻"语义（代码注释已说明） |
| Q-05 | 取消边界：`NOW() == start - 30min` | **允许**取消（判定为 `now > deadline` 才拒绝） | 与"提前 30 分钟"的直觉可能差 1 秒 | 明确边界取开还是闭；用例按闭区间断言 |
| Q-06 | 仅有 `RESERVED` 订单的柜格能否切维护 | **允许**（M7 只拒绝 `IN_USE/OVERDUE`） | 已预约用户到店无法签到，系统无通知/补偿 | 明确运维流程：是否先强制取消、是否通知 |
| Q-07 | `OVERDUE` 是否有终态或费用 | 无。逾期后订单可一直保持 `OVERDUE`，直到用户取件或被强制取消 | 长期占用、占用率长期偏高；无超时费 | 明确逾期策略（自动计费/自动清理/人工介入） |
| Q-08 | 强制取消 `IN_USE` 订单 | 直接置 `FORCE_CANCELLED` 并释放时段，**不校验行李是否取出** | 系统显示柜格可用，物理上行李还在 | 明确是否要求先开柜/登记，或至少二次确认 |
| Q-09 | 批量建柜 `prefix` 字符集 | 只校验长度 1~8，允许空格、中文、特殊字符 | 生成难以操作的柜格编号 | 明确编号规范并加校验 |
| Q-10 | 部署机时区不是 `+08:00` | 系统按 naive DATETIME 直接比较，不做时区转换 | 所有时间规则整体偏移 | 在启动时校验时区，或在文档中写死部署要求 |
| Q-11 | `min_advance_minutes` 配为 0 | 允许预约"当前时刻"，与 BR-03 默认 5 分钟冲突 | 边界用例预期随配置变化 | 明确该配置是否允许 0，以及测试基线是否锁定默认值 |
| Q-12 | M10 用户名模糊匹配的大小写敏感性 | 取决于 `utf8mb4_general_ci`，**不区分大小写** | 运营搜 `User01` 能搜到 `user01` | 明确是否需要区分；用例按不区分断言 |
