# 测试核验指南：MySQL 事实核对 + Fiddler 抓包对比

> 适用对象：本项目的接口测试、Selenium/JMeter 结果复核、缺陷复现。
>
> 本文的 SQL 和接口行为均以当前工程实际实现为准：
>
> - 数据库：`luggage_locker`，MySQL `8.0.40`，表默认排序规则 `utf8mb4_general_ci`
> - 表结构：`sql/01-schema.sql` 与 `SHOW COLUMNS` / `SHOW INDEX` 实测一致
> - 接口实现：`backend/app/api/v1/*.py`、`backend/app/services/*.py`
> - 本文所有查询均为只读 `SELECT`，不修改订单、柜格或日志
>
> **重要原则**：HTTP 成功只代表接口返回成功，不代表数据库事实正确。
> 预约类测试必须同时核对订单、时段占用、柜格派生状态和状态日志，不能只看“请求成功率”。

## 0. 先确认四个数据事实

### 0.1 柜格“占用状态”不是一列

实际表 `cabinets` 只有：

```text
id, group_id, type_id, code, physical_status, remark, created_at, updated_at
```

其中 `cabinets.physical_status` 是**运维维度**，只有：

```text
AVAILABLE / MAINTENANCE / DISABLED
```

它**不会**因为用户预约而变成 `RESERVED` 或 `IN_USE`。

“已预约 / 使用中”是服务层按订单实时派生出来的展示状态，不落库。
因此核验“预约成功后柜格状态”时，不能查一个不存在的 `cabinets.status`，
而应核对：

1. `cabinets.physical_status` 是否仍为 `AVAILABLE`；
2. 所属柜体、寄存点、规格是否仍可服务；
3. 指定时刻是否有且只有一条占用类订单；
4. 指定时刻是否有且只有一条对应时段占用记录。

派生状态的优先级是：

```text
MAINTENANCE > DISABLED > UNAVAILABLE（柜体/寄存点不可用）
            > IN_USE（存在 IN_USE/OVERDUE）
            > RESERVED（存在覆盖查询时刻的 RESERVED）
            > AVAILABLE
```

### 0.2 占用类和终态

实际 `reservations.status` 的取值为：

```text
RESERVED / IN_USE / OVERDUE / COMPLETED / CANCELLED / EXPIRED / FORCE_CANCELLED
```

占用类只有三个：

```text
RESERVED / IN_USE / OVERDUE
```

终态是：

```text
COMPLETED / CANCELLED / EXPIRED / FORCE_CANCELLED
```

关键实现事实：

- `RESERVED`：已预约，尚未签到；`reservation_slots` 有记录；
- `IN_USE`：已签到，行李在柜内；`reservation_slots` **仍然保留**；
- `OVERDUE`：逾期未取，行李仍在柜内；`reservation_slots` **仍然保留**；
- `CANCELLED`：用户取消，同一事务删除全部 `reservation_slots`；
- `COMPLETED`：用户取件，立即释放剩余时段；
- `EXPIRED`：超时未签到，系统任务释放时段；
- `FORCE_CANCELLED`：管理员强制取消，释放时段。

所以“终态订单不应再占用时段”是强校验；`IN_USE/OVERDUE` 反而必须有完整时段。

### 0.3 快照字段不要用当前主数据反推历史

订单里保存了下单时的快照：

```text
cabinet_code_snapshot
point_name_snapshot
unit_price
amount
checkin_deadline
```

它们只应和**下单当时**的主数据/配置一致。若之后管理员改了柜格编号、寄存点名称、
规格价格或系统参数，历史订单与当前主数据不一致**不一定是缺陷**。

本文中标记为“即时快照”的断言，只适用于：

- 本轮刚创建；
- 创建后没有改过对应主数据或系统配置。

### 0.4 时间粒度以哪个字段为准

实际创建预约时，时间拆分读取的是：

```text
system_config.config_key = 'slot_minutes'
```

不是 `cabinet_types.slot_minutes`。两者当前都为 `30`，但核验时不要混用。

当前实测配置：

```text
slot_minutes               = 30
min_slot_count             = 1
max_slot_count             = 144
min_advance_minutes        = 5
max_advance_days           = 7
checkin_grace_minutes      = 30
checkin_early_minutes      = 15
cancel_ahead_minutes       = 30
```

`slot_count` 和 `checkin_deadline` 没有单独的“下单时粒度/宽限期快照”字段。
如果测试期间改过 `slot_minutes` 或 `checkin_grace_minutes`，再拿当前配置去反推旧订单，
可能产生假失败。本文的 SQL 默认测试期间配置稳定。

## 1. 连接数据库与设置变量

### 1.1 连接

在测试机上使用 MySQL 客户端（命令行或 Workbench）连接测试库：

```powershell
mysql -u <DB_USER> -p --default-character-set=utf8mb4 luggage_locker
```

不要在命令、截图或文档里写真实密码；`-p` 会交互式询问密码。

### 1.2 变量与排序规则

每次新建数据库会话后执行一次：

```sql
SET @order_no := _utf8mb4'LZ20260101ABCDEF12' COLLATE utf8mb4_general_ci;
SET @user_id := 123;
SET @idem := _utf8mb4'manual-check-0001' COLLATE utf8mb4_general_ci;
SET @check_time := CAST('2026-01-01 10:30:00' AS DATETIME);

SET @slot_minutes := (
  SELECT CAST(config_value AS UNSIGNED)
  FROM system_config
  WHERE config_key = 'slot_minutes'
);

SET @grace_minutes := (
  SELECT CAST(config_value AS UNSIGNED)
  FROM system_config
  WHERE config_key = 'checkin_grace_minutes'
);
```

把示例值替换为：

- `@order_no`：接口响应中的 `order_no`；
- `@user_id`：下单用户的 `user_id`；
- `@idem`：本次请求使用的 `idempotency_key`；
- `@check_time`：预约区间内的一个时刻，例如 `10:30:00`。

**实测注意：排序规则 1267 错误**

当前表是 `utf8mb4_general_ci`，而 MySQL 8 客户端会话可能使用
`utf8mb4_0900_ai_ci`。直接写：

```sql
SET @order_no := 'LZ...';
```

再用 `WHERE order_no = @order_no` 可能报：

```text
Illegal mix of collations (utf8mb4_general_ci,IMPLICIT)
and (utf8mb4_0900_ai_ci,IMPLICIT)
```

因此本文统一使用：

```sql
_utf8mb4'...' COLLATE utf8mb4_general_ci
```

或在使用处加：

```sql
WHERE r.order_no = @order_no COLLATE utf8mb4_general_ci
```

如果你们的库不是 `utf8mb4_general_ci`，按实际库调整，不要照抄排序规则。

### 1.3 并发测试后的查询时机

必须等 JMeter / pytest / UI 操作**全部结束**后再查数据库。
不要在请求线程还在跑时边跑边查，否则看到的是中间状态。

如果需要一次事务内看到一致快照，可以先执行：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION WITH CONSISTENT SNAPSHOT;

-- 在这里连续执行本文的 SELECT

COMMIT;
```

## 2. 预约成功后的订单与柜格核验

### 2.1 订单主记录、金额、快照和可服务状态

**验证目的**

- 确认订单确实只有一条；
- 确认时间顺序、时段数、金额计算正确；
- 确认订单快照与当前主数据一致（仅限本轮新建、未改主数据）；
- 确认柜格物理状态、柜体、寄存点、规格处于可服务状态。

**SQL**

```sql
SELECT
    r.order_no,
    r.user_id,
    r.status,
    r.start_time,
    r.end_time,
    r.slot_count,
    r.luggage_size,
    r.luggage_count,
    r.unit_price,
    r.amount,
    r.pay_status,
    r.idempotency_key,
    r.checkin_deadline,
    r.created_at,

    -- 金额是硬不变量：amount = unit_price * slot_count
    ROUND(r.unit_price * r.slot_count, 2) AS expected_amount,
    (r.amount = ROUND(r.unit_price * r.slot_count, 2)) AS amount_ok,

    -- 时间顺序与时段数
    (r.start_time < r.end_time) AS time_order_ok,
    (
      r.slot_count =
      CAST(TIMESTAMPDIFF(MINUTE, r.start_time, r.end_time) / @slot_minutes AS UNSIGNED)
    ) AS slot_count_ok,

    -- 以下两项依赖当前配置，测试期间配置未变时才断言
    (
      r.checkin_deadline =
      DATE_ADD(r.start_time, INTERVAL @grace_minutes MINUTE)
    ) AS checkin_deadline_ok,

    -- 以下三项是“即时快照”断言：创建后未改主数据才应全为 1
    (r.cabinet_code_snapshot = c.code) AS cabinet_snapshot_ok,
    (r.point_name_snapshot = p.name) AS point_snapshot_ok,
    (r.cabinet_type_id = c.type_id) AS cabinet_type_ok,
    (g.point_id = r.point_id) AS group_point_ok,

    p.status AS point_status,
    g.status AS group_status,
    c.physical_status,
    ct.is_active AS type_active,
    ct.size_level AS type_size_level,
    ct.price_per_slot AS current_price
FROM reservations r
JOIN cabinets c
  ON c.id = r.cabinet_id
JOIN cabinet_groups g
  ON g.id = c.group_id
JOIN storage_points p
  ON p.id = r.point_id
JOIN cabinet_types ct
  ON ct.id = r.cabinet_type_id
WHERE r.order_no = @order_no;
```

**预期判定**

| 字段/标记 | 预期 |
|---|---|
| 返回行数 | 恰好 1 行；0 行说明订单不存在或 `@order_no` 写错 |
| `status` | 预约成功阶段为 `RESERVED`；签到后为 `IN_USE` |
| `time_order_ok` | `1` |
| `amount_ok` | `1` |
| `slot_count_ok` | `1`（配置未变时） |
| `checkin_deadline_ok` | `1`（宽限期配置未变时） |
| `luggage_count` | `1`（本期固定） |
| `pay_status` | `UNPAID`（本期不接支付，不能拿它判断业务成功） |
| `point_status` / `group_status` / `physical_status` | `OPEN` / `NORMAL` / `AVAILABLE` |
| `type_active` | `1` |
| `cabinet_snapshot_ok` / `point_snapshot_ok` / `cabinet_type_ok` | 即时新建订单应为 `1` |
| `group_point_ok` | `1`，柜体必须属于订单的寄存点 |
| `current_price` | 仅供对照；历史订单不要用当前价格反推 `unit_price` |

如果 `amount_ok=0`，优先怀疑金额计算或快照写入；
如果 `slot_count_ok=0`，先确认测试期间是否改过 `slot_minutes`，再怀疑订单写入。

### 2.2 时段占用记录是否“完整且没有多余”

**验证目的**

`reservation_slots` 是防超卖的核心事实表。一个 `RESERVED/IN_USE/OVERDUE` 订单必须有：

- 正好 `slot_count` 条记录；
- 每条记录的 `cabinet_id` 都等于订单 `cabinet_id`；
- `slot_start` 从 `start_time` 开始，每 `slot_minutes` 一条；
- 最后一条是 `end_time - slot_minutes`；
- 没有越界、重复、错柜格、缺失。

**SQL**

```sql
SELECT
    r.order_no,
    r.slot_count,
    COUNT(s.id) AS actual_slot_rows,
    COUNT(DISTINCT s.slot_start) AS distinct_slot_starts,
    CAST(
      TIMESTAMPDIFF(MINUTE, r.start_time, r.end_time) / @slot_minutes
      AS UNSIGNED
    ) AS expected_slot_rows,
    MIN(s.slot_start) AS min_slot_start,
    DATE_SUB(r.end_time, INTERVAL @slot_minutes MINUTE) AS expected_max_slot_start,
    MAX(s.slot_start) AS max_slot_start,
    COALESCE(SUM(s.cabinet_id <> r.cabinet_id), 0) AS wrong_cabinet_rows,
    COALESCE(SUM(s.slot_start < r.start_time OR s.slot_start >= r.end_time), 0)
      AS out_of_range_rows,
    COALESCE(
      SUM(MOD(TIMESTAMPDIFF(MINUTE, r.start_time, s.slot_start), @slot_minutes) <> 0),
      0
    ) AS misaligned_rows,

    CASE
      WHEN COUNT(s.id) = r.slot_count
       AND COUNT(DISTINCT s.slot_start) = r.slot_count
       AND COALESCE(MIN(s.slot_start), r.start_time) = r.start_time
       AND COALESCE(
             MAX(s.slot_start),
             DATE_SUB(r.end_time, INTERVAL @slot_minutes MINUTE)
           ) = DATE_SUB(r.end_time, INTERVAL @slot_minutes MINUTE)
       AND COALESCE(SUM(s.cabinet_id <> r.cabinet_id), 0) = 0
       AND COALESCE(
             SUM(s.slot_start < r.start_time OR s.slot_start >= r.end_time),
             0
           ) = 0
       AND COALESCE(
             SUM(MOD(TIMESTAMPDIFF(MINUTE, r.start_time, s.slot_start), @slot_minutes) <> 0),
             0
           ) = 0
      THEN 'PASS'
      ELSE 'FAIL'
    END AS slot_check
FROM reservations r
LEFT JOIN reservation_slots s
  ON s.reservation_id = r.id
WHERE r.order_no = @order_no
GROUP BY r.id;
```

**预期判定**

```text
actual_slot_rows     = slot_count = expected_slot_rows
distinct_slot_starts = slot_count
min_slot_start       = start_time
max_slot_start       = end_time - slot_minutes
wrong_cabinet_rows   = 0
out_of_range_rows    = 0
misaligned_rows      = 0
slot_check           = PASS
```

**说明**

- 这是对 `RESERVED / IN_USE / OVERDUE` 的检查；
- 对 `CANCELLED / COMPLETED / EXPIRED / FORCE_CANCELLED`，预期不是“完整”，
  而是“0 条”，用 2.6 的终态查询；
- 只有 `COUNT` 正确还不够：`COUNT` 正确但时间错位，同样会在后续冲突判断中造成超卖或误判。

### 2.3 指定时刻的柜格状态与占用唯一性

**验证目的**

在预约区间内取一个时刻 `@check_time`，确认：

- 订单确实覆盖该时刻；
- 该柜格在该时刻只有 1 条占用订单；
- 该时刻只有 1 条时段记录；
- `physical_status` 仍是运维状态；
- 按当前订单推导出的状态应为 `RESERVED`（未签到）或 `IN_USE`（已签到）。

**SQL**

```sql
SELECT
    c.id AS cabinet_id,
    c.code AS cabinet_code,
    c.physical_status,
    p.status AS point_status,
    g.status AS group_status,
    ct.is_active AS type_active,

    (
      SELECT COUNT(*)
      FROM reservations r2
      WHERE r2.cabinet_id = c.id
        AND r2.status IN ('RESERVED', 'IN_USE', 'OVERDUE')
        AND @check_time >= r2.start_time
        AND @check_time < r2.end_time
    ) AS active_orders_at_check_time,

    (
      SELECT COUNT(*)
      FROM reservation_slots s2
      WHERE s2.cabinet_id = c.id
        AND @check_time >= s2.slot_start
        AND @check_time < DATE_ADD(s2.slot_start, INTERVAL @slot_minutes MINUTE)
    ) AS active_slots_at_check_time,

    CASE
      WHEN c.physical_status = 'MAINTENANCE' THEN 'MAINTENANCE'
      WHEN c.physical_status = 'DISABLED' THEN 'DISABLED'
      WHEN p.status <> 'OPEN' OR g.status <> 'NORMAL' THEN 'UNAVAILABLE'
      WHEN EXISTS (
        SELECT 1
        FROM reservations r3
        WHERE r3.cabinet_id = c.id
          AND r3.status IN ('IN_USE', 'OVERDUE')
      ) THEN 'IN_USE'
      WHEN EXISTS (
        SELECT 1
        FROM reservations r4
        WHERE r4.cabinet_id = c.id
          AND r4.status = 'RESERVED'
          AND @check_time >= r4.start_time
          AND @check_time < r4.end_time
      ) THEN 'RESERVED'
      ELSE 'AVAILABLE'
    END AS derived_status_at_check_time
FROM cabinets c
JOIN cabinet_groups g
  ON g.id = c.group_id
JOIN storage_points p
  ON p.id = g.point_id
JOIN cabinet_types ct
  ON ct.id = c.type_id
WHERE c.id = (
  SELECT cabinet_id
  FROM reservations
  WHERE order_no = @order_no
);
```

**预期判定**

预约成功后、未签到、`@check_time` 位于区间内：

```text
physical_status                 = AVAILABLE
point_status                    = OPEN
group_status                    = NORMAL
type_active                     = 1
active_orders_at_check_time     = 1
active_slots_at_check_time      = 1
derived_status_at_check_time    = RESERVED
```

签到后（`IN_USE`）同一时刻：

```text
derived_status_at_check_time    = IN_USE
active_orders_at_check_time     = 1
active_slots_at_check_time      = 1
```

取消后同一时刻：

```text
active_orders_at_check_time     = 0
active_slots_at_check_time      = 0
derived_status_at_check_time    = AVAILABLE
```

**不要把 `physical_status` 的 `AVAILABLE` 当成“没人预约”**。
它只表示柜格没有被运维停用；占用情况必须看订单和时段。

> 本查询是“指定时刻”的核验。Q7 柜格详情接口使用的是“当前时刻”，
> 若订单在未来，`derived_status` 可能显示 `AVAILABLE`。不要用未来的
> `@check_time` 去对照当前时刻接口的结果。

## 3. 取消后的状态核验

### 3.1 取消订单、释放时段、写入审计

**验证目的**

- 订单状态变为 `CANCELLED`；
- `cancelled_at` 已写入；
- 该订单的 `reservation_slots` 已全部删除；
- 只有一条 `RESERVED -> CANCELLED` 审计日志；
- 接口返回的 `released_slot_count` 应等于 `slot_count`。

**SQL**

```sql
SELECT
    r.order_no,
    r.status,
    r.cancelled_at,
    r.cancel_reason,
    r.slot_count,
    r.created_at,

    (
      SELECT COUNT(*)
      FROM reservation_slots s
      WHERE s.reservation_id = r.id
    ) AS remaining_slot_rows,

    (
      SELECT COUNT(*)
      FROM reservation_status_logs l
      WHERE l.reservation_id = r.id
        AND l.to_status = 'CANCELLED'
    ) AS cancel_log_count,

    (
      SELECT COUNT(*)
      FROM reservation_status_logs l
      WHERE l.reservation_id = r.id
        AND l.from_status = 'RESERVED'
        AND l.to_status = 'CANCELLED'
        AND l.operator_type = 'USER'
    ) AS valid_user_cancel_logs,

    (r.cancelled_at IS NOT NULL) AS cancelled_at_ok
FROM reservations r
WHERE r.order_no = @order_no;
```

**预期判定**

```text
status                    = CANCELLED
cancelled_at              != NULL
remaining_slot_rows       = 0
cancel_log_count          = 1
valid_user_cancel_logs    = 1
cancelled_at_ok           = 1
```

补充判断：

- 取消接口返回 `released_slot_count` 应等于 `r.slot_count`；
- `cancel_reason` 可以为 `NULL`，因为用户取消原因本身可选；
- 不要要求 `cancel_reason` 一定有值；
- 如果 `remaining_slot_rows > 0`，柜格仍会被占用，属于严重缺陷；
- 如果 `cancel_log_count > 1`，检查是否重复写入日志或并发取消没有做到条件更新。

### 3.2 取消后的状态时间线

**SQL**

```sql
SELECT
    l.id,
    l.from_status,
    l.to_status,
    l.operator_type,
    l.operator_id,
    l.remark,
    l.created_at
FROM reservation_status_logs l
JOIN reservations r
  ON r.id = l.reservation_id
WHERE r.order_no = @order_no
ORDER BY l.id;
```

正常用户取消应只有两条：

```text
NULL      -> RESERVED    USER
RESERVED  -> CANCELLED   USER
```

**预期判定**

- 第一条 `from_status IS NULL`，`to_status='RESERVED'`；
- 第二条 `from_status='RESERVED'`，`to_status='CANCELLED'`；
- 两条的 `operator_type='USER'`；
- `operator_id` 应等于订单的 `user_id`；
- 不应出现 `CANCELLED` 之后的任何日志（终态不可再变更）。

## 4. 重复提交后的记录数量

### 4.1 按 `(user_id, idempotency_key)` 核对订单数

**验证目的**

同一个用户使用同一个 `idempotency_key` 重复提交 N 次，数据库中只能有 1 条订单。
HTTP 层可能是：

```text
第 1 次：201 + idempotent_replay=false
第 2..N 次：200 + idempotent_replay=true
```

但数据库事实必须始终是 1 条。

**SQL**

```sql
SELECT
    r.user_id,
    r.idempotency_key,
    COUNT(*) AS order_rows,
    COUNT(DISTINCT r.order_no) AS distinct_order_nos,
    MIN(r.order_no) AS first_order_no,
    MIN(r.created_at) AS first_created_at,
    MAX(r.created_at) AS last_created_at
FROM reservations r
WHERE r.user_id = @user_id
  AND r.idempotency_key = @idem
GROUP BY r.user_id, r.idempotency_key;
```

**预期判定**

```text
返回行数              = 1
order_rows            = 1
distinct_order_nos    = 1
first_created_at      = last_created_at
```

如果返回 0 行：

- 第一次请求就没有成功；或者
- `@user_id` / `@idem` 写错；或者
- 请求用了另一个幂等键。

如果 `order_rows > 1`：

- 幂等唯一索引或应用层幂等逻辑失效；
- 这是高优先级缺陷，不应仅凭“多次请求都返回 200”判定通过。

### 4.2 全局重复检查

```sql
-- 同一用户 + 同一幂等键只能有一行
SELECT
    user_id,
    idempotency_key,
    COUNT(*) AS n
FROM reservations
GROUP BY user_id, idempotency_key
HAVING COUNT(*) > 1;

-- 订单号必须唯一
SELECT
    order_no,
    COUNT(*) AS n
FROM reservations
GROUP BY order_no
HAVING COUNT(*) > 1;
```

**预期判定**

两条查询都应返回 0 行。

实际唯一索引：

```text
uk_reservations_user_idem (user_id, idempotency_key)
uk_reservations_order_no  (order_no)
```

它们能兜底，但**不要只依赖索引存在**：索引存在不等于业务一定按幂等键返回原订单，
还要核对响应中的 `order_no` 是否与第一次相同、`idempotent_replay=true`。

## 5. 时间重叠与超卖核验

### 5.1 同一柜格的订单区间两两重叠

**验证目的**

占用类订单的区间必须满足左闭右开语义：

```text
a.start_time < b.end_time AND b.start_time < a.end_time
```

这是“同一柜格同一时刻只有一单”的订单级检查。
即使 `reservation_slots` 有唯一索引，也要单独查，因为：
时段记录可能缺失、写入错误，或订单状态与时段不一致。

**SQL**

```sql
SELECT
    a.order_no AS order_a,
    b.order_no AS order_b,
    a.cabinet_id,
    a.status AS status_a,
    b.status AS status_b,
    a.start_time AS a_start,
    a.end_time AS a_end,
    b.start_time AS b_start,
    b.end_time AS b_end
FROM reservations a
JOIN reservations b
  ON b.cabinet_id = a.cabinet_id
 AND b.id > a.id
WHERE a.status IN ('RESERVED', 'IN_USE', 'OVERDUE')
  AND b.status IN ('RESERVED', 'IN_USE', 'OVERDUE')
  AND a.start_time < b.end_time
  AND b.start_time < a.end_time
ORDER BY a.cabinet_id, a.start_time, a.order_no;
```

**预期判定**

返回 0 行。

**边界说明**

以下两个订单**不算重叠**，不应被查出：

```text
A: 10:00 - 11:00
B: 11:00 - 12:00
```

因为 `A.end_time = B.start_time`，左闭右开语义下是合法衔接。

### 5.2 同一柜格同一时段的占用记录重复

**SQL**

```sql
SELECT
    s.cabinet_id,
    s.slot_start,
    COUNT(*) AS row_count
FROM reservation_slots s
JOIN reservations r
  ON r.id = s.reservation_id
WHERE r.status IN ('RESERVED', 'IN_USE', 'OVERDUE')
GROUP BY s.cabinet_id, s.slot_start
HAVING COUNT(*) > 1
ORDER BY s.cabinet_id, s.slot_start;
```

**预期判定**

返回 0 行。

实际唯一索引：

```text
uk_slots_cabinet_slot (cabinet_id, slot_start)
```

如果这个查询有结果，说明：

- 唯一索引缺失/被删除；或
- 测试写入了脏数据；或
- 表结构不是当前版本。

### 5.3 时段与订单的柜格不一致

**SQL**

```sql
SELECT
    s.id AS slot_id,
    s.reservation_id,
    s.cabinet_id AS slot_cabinet_id,
    r.cabinet_id AS order_cabinet_id
FROM reservation_slots s
JOIN reservations r
  ON r.id = s.reservation_id
WHERE s.cabinet_id <> r.cabinet_id;
```

**预期判定**

返回 0 行。

**验证目的**

```text
COMPLETED
CANCELLED
EXPIRED
FORCE_CANCELLED
```

## 7. 无效状态与不一致组合

`reservations.status` 是 MySQL `ENUM`，理论上写不进非法值。
但为了防御手工改库、旧表结构、数据导入和迁移问题，仍然做两层检查。

### 7.1 非法状态值

```sql
SELECT
    order_no,
    status
FROM reservations
WHERE status NOT IN (
  'RESERVED', 'IN_USE', 'OVERDUE',
  'COMPLETED', 'CANCELLED', 'EXPIRED', 'FORCE_CANCELLED'
);
```

**预期判定**

返回 0 行。

### 7.2 状态、时间戳、金额、时间对齐的不一致

**验证目的**

不同状态对生命周期时间戳有固定要求：

| 状态 | `checked_in_at` | `completed_at` | `cancelled_at` |
|---|---|---|---|
| `RESERVED` | NULL | NULL | NULL |
| `IN_USE` | 非 NULL | NULL | NULL |
| `OVERDUE` | 非 NULL | NULL | NULL |
| `COMPLETED` | 非 NULL | 非 NULL | NULL |
| `CANCELLED` | NULL | NULL | 非 NULL |
| `EXPIRED` | NULL | NULL | 非 NULL |
| `FORCE_CANCELLED` | 可为 NULL 或非 NULL | NULL | 非 NULL |

**SQL**

```sql
SELECT
    r.order_no,
    r.status,
    r.start_time,
    r.end_time,
    r.slot_count,
    r.luggage_count,
    r.unit_price,
    r.amount,
    r.checked_in_at,
    r.completed_at,
    r.cancelled_at,
    r.cancel_reason,

    CASE
      WHEN r.start_time >= r.end_time
        THEN 'start_time >= end_time'

      WHEN r.slot_count = 0
        THEN 'slot_count = 0'

      WHEN r.luggage_count <> 1
        THEN 'luggage_count <> 1'

      WHEN SECOND(r.start_time) <> 0
        OR SECOND(r.end_time) <> 0
        OR MOD(MINUTE(r.start_time), @slot_minutes) <> 0
        OR MOD(MINUTE(r.end_time), @slot_minutes) <> 0
        THEN 'time not aligned'

      WHEN r.amount <> ROUND(r.unit_price * r.slot_count, 2)
        THEN 'amount mismatch'

      WHEN r.status = 'RESERVED'
        AND (r.checked_in_at IS NOT NULL
             OR r.completed_at IS NOT NULL
             OR r.cancelled_at IS NOT NULL)
        THEN 'RESERVED has lifecycle timestamp'

      WHEN r.status = 'IN_USE'
        AND (r.checked_in_at IS NULL
             OR r.completed_at IS NOT NULL
             OR r.cancelled_at IS NOT NULL)
        THEN 'IN_USE timestamps invalid'

      WHEN r.status = 'OVERDUE'
        AND (r.checked_in_at IS NULL
             OR r.completed_at IS NOT NULL
             OR r.cancelled_at IS NOT NULL)
        THEN 'OVERDUE timestamps invalid'

      WHEN r.status = 'COMPLETED'
        AND (r.checked_in_at IS NULL
             OR r.completed_at IS NULL
             OR r.cancelled_at IS NOT NULL)
        THEN 'COMPLETED timestamps invalid'

      WHEN r.status = 'CANCELLED'
        AND (r.checked_in_at IS NOT NULL
             OR r.completed_at IS NOT NULL
             OR r.cancelled_at IS NULL)
        THEN 'CANCELLED timestamps invalid'

      WHEN r.status = 'EXPIRED'
        AND (r.checked_in_at IS NOT NULL
             OR r.completed_at IS NOT NULL
             OR r.cancelled_at IS NULL)
        THEN 'EXPIRED timestamps invalid'

      WHEN r.status = 'FORCE_CANCELLED'
        AND (r.completed_at IS NOT NULL OR r.cancelled_at IS NULL)
        THEN 'FORCE_CANCELLED timestamps invalid'

      ELSE NULL
    END AS problem
FROM reservations r
HAVING problem IS NOT NULL
ORDER BY r.order_no;
```

**预期判定**

返回 0 行。

**说明**

- `CANCELLED` 的 `cancel_reason` 可以为 NULL，不在这个查询里强制；
- `EXPIRED` 和 `FORCE_CANCELLED` 的 `cancel_reason` 通常由任务/管理员写入，
  但核验重点是状态、时间和时段释放，不要只凭原因文案判断；
- `time not aligned` 使用当前 `@slot_minutes`；如果测试期间改过配置，
  对历史订单可能产生假失败，需先确认配置历史。

### 7.3 状态与时段数量的交叉检查

```sql
-- 占用类：必须有时段
SELECT
    r.order_no,
    r.status,
    r.slot_count,
    (SELECT COUNT(*) FROM reservation_slots s WHERE s.reservation_id = r.id)
      AS actual_slot_rows
FROM reservations r
WHERE r.status IN ('RESERVED', 'IN_USE', 'OVERDUE')
  AND (SELECT COUNT(*) FROM reservation_slots s WHERE s.reservation_id = r.id)

-- 终态：必须没有时段
SELECT
    r.order_no,
    r.status
FROM reservations r
WHERE r.status IN ('COMPLETED', 'CANCELLED', 'EXPIRED', 'FORCE_CANCELLED')
  AND EXISTS (
    SELECT 1
    FROM reservation_slots s
    WHERE s.reservation_id = r.id
  );
```

**预期判定**

两条查询都应返回 0 行。

## 8. 状态审计日志链

### 8.1 每个订单必须恰好有一条创建日志

**SQL**

```sql
SELECT
    r.order_no,
    COUNT(l.id) AS total_logs,
    SUM(CASE WHEN l.from_status IS NULL AND l.to_status = 'RESERVED' THEN 1 ELSE 0 END)
      AS initial_logs
FROM reservations r
LEFT JOIN reservation_status_logs l
  ON l.reservation_id = r.id
GROUP BY r.id
HAVING initial_logs <> 1;
```

**预期判定**

返回 0 行。

正常创建日志：

```text
from_status = NULL
to_status   = RESERVED
operator_type = USER
operator_id = 下单用户 id
```

### 8.2 当前状态必须等于最后一条日志的 `to_status`

**SQL**

```sql
SELECT
    r.order_no,
    r.status,
    l.to_status AS latest_log_status,
    l.from_status AS latest_log_from,
    l.created_at AS latest_log_at
FROM reservations r
LEFT JOIN reservation_status_logs l
  ON l.id = (
    SELECT MAX(l2.id)
    FROM reservation_status_logs l2
    WHERE l2.reservation_id = r.id
  )
WHERE r.status <> COALESCE(l.to_status, '')
   OR l.id IS NULL;
```

**预期判定**

返回 0 行。

### 8.3 日志链必须首尾相接

**SQL**

```sql
WITH log_chain AS (
  SELECT
      l.reservation_id,
      l.id,
      l.from_status,
      l.to_status,
      LAG(l.to_status) OVER (
        PARTITION BY l.reservation_id
        ORDER BY l.id
      ) AS prev_to_status
  FROM reservation_status_logs l
)
SELECT
    reservation_id,
    id,
    from_status,
    to_status,
    prev_to_status
FROM log_chain
WHERE (prev_to_status IS NULL AND from_status IS NOT NULL)
   OR (prev_to_status IS NOT NULL AND from_status <> prev_to_status);
```

**预期判定**

返回 0 行。

### 8.4 操作人类型与目标状态匹配（可选但推荐）

**SQL**

```sql
SELECT
    r.order_no,
    l.id AS log_id,
    l.from_status,
    l.to_status,
    l.operator_type,
    l.operator_id,
    r.user_id
FROM reservation_status_logs l
JOIN reservations r
  ON r.id = l.reservation_id
WHERE
  -- 创建、用户取消、签到、用户取件：必须是本人 USER
  (
    l.to_status IN ('RESERVED', 'IN_USE', 'CANCELLED', 'COMPLETED')
    AND (
      l.operator_type <> 'USER'
      OR l.operator_id IS NULL
      OR l.operator_id <> r.user_id
    )
  )
  OR
  -- 系统超时释放、系统标记逾期：SYSTEM，operator_id 为空
  (
    l.to_status IN ('EXPIRED', 'OVERDUE')
    AND (
      l.operator_type <> 'SYSTEM'
      OR l.operator_id IS NOT NULL
    )
  )
  OR
  -- 管理员强制取消：ADMIN，operator_id 非空
  (
    l.to_status = 'FORCE_CANCELLED'
    AND (
      l.operator_type <> 'ADMIN'
      OR l.operator_id IS NULL
    )
  );
```

**预期判定**

返回 0 行。

**注意**

- 用户取消、签到、取件都记录 `operator_type='USER'`；
- `EXPIRED` 和 `OVERDUE` 由任务记录为 `SYSTEM`；
- `FORCE_CANCELLED` 由管理员记录为 `ADMIN`；
- `COMPLETED` 的来源可能是 `IN_USE` 或 `OVERDUE`，但操作人仍是用户。

## 9. 过期释放与强制取消的专项核验

### 9.1 超时未签到（`EXPIRED`）

**SQL**

```sql
SELECT
    r.order_no,
    r.status,
    r.cancelled_at,
    r.cancel_reason,
    r.slot_count,
    (SELECT COUNT(*) FROM reservation_slots s WHERE s.reservation_id = r.id)
      AS remaining_slot_rows,
    (SELECT COUNT(*) FROM reservation_status_logs l
      WHERE l.reservation_id = r.id
        AND l.from_status = 'RESERVED'
        AND l.to_status = 'EXPIRED'
        AND l.operator_type = 'SYSTEM'
        AND l.operator_id IS NULL)
      AS valid_expire_logs
FROM reservations r
WHERE r.order_no = @order_no;
```

**预期判定**

```text
status              = EXPIRED
cancelled_at        != NULL
remaining_slot_rows = 0
valid_expire_logs   = 1
```

补充：

- `EXPIRED` 也会写 `cancelled_at` 和 `cancel_reason`；
- 任务只处理 `RESERVED` 且 `checkin_deadline <= NOW()` 的订单；

## 10. 索引与约束核验（结构层）

数据正确性查询之外，再确认防超卖和幂等的唯一索引确实存在：

```sql
SELECT
    table_name,
    index_name,
    non_unique,
    GROUP_CONCAT(column_name ORDER BY seq_in_index) AS columns_in_order
FROM information_schema.statistics
WHERE table_schema = DATABASE()
  AND (
    (table_name = 'reservations'
     AND index_name IN ('uk_reservations_user_idem', 'uk_reservations_order_no'))
    OR
    (table_name = 'reservation_slots'
     AND index_name = 'uk_slots_cabinet_slot')
  )
GROUP BY table_name, index_name, non_unique
ORDER BY table_name, index_name;
```

**预期判定**

| 表 | 索引 | `non_unique` | 列顺序 |
|---|---|---|---|
| `reservations` | `uk_reservations_user_idem` | 0 | `user_id,idempotency_key` |
| `reservations` | `uk_reservations_order_no` | 0 | `order_no` |
| `reservation_slots` | `uk_slots_cabinet_slot` | 0 | `cabinet_id,slot_start` |

**说明**

索引是第二道防线，不是全部证据：

- `uk_slots_cabinet_slot` 防同一柜格同一时段重复占用；
- `uk_reservations_user_idem` 防同一用户同一幂等键重复建单；
- 但“订单区间是否重叠”“终态是否释放”“日志链是否正确”仍然必须用前面的数据查询确认。

## 11. 并发场景的判定口径

### 11.1 同柜格抢同一时段

假设 N 个用户同时预约同一柜格、同一时段：

| 观察项 | 通过条件 |
|---|---|
| HTTP | 恰好 1 个 `201`，其余 `409 CABINET_TIME_CONFLICT` |
| 订单 | 数据库中该柜格该时段只有 1 条占用类订单 |
| 时段 | 该柜格该时段只有 1 条 `reservation_slots` 记录 |
| 区间 | 5.1 的订单区间重叠查询返回 0 行 |
| 唯一索引 | 5.2 的重复查询返回 0 行 |
| 503 | 0；`503 LOCK_TIMEOUT` 是环境/锁等待信号，不算正常业务冲突 |

不能因为“HTTP 201 只有 1 个”就停止核验；还要看订单、时段和区间。

### 11.2 重复提交

| 观察项 | 通过条件 |
|---|---|
| HTTP | 1 个 `201`，其余 `200` 且 `idempotent_replay=true` |
| 订单号 | 所有成功响应返回同一个 `order_no` |
| 订单数 | 按 `(user_id, idempotency_key)` 统计为 1 |
| 时段数 | 该订单的 `reservation_slots` 仍等于 `slot_count`，没有翻倍 |
| 日志 | 只有一条创建日志，没有重复的 `RESERVED` 日志 |

### 11.3 并发取消

| 观察项 | 通过条件 |
|---|---|
| HTTP | 1 个 `200`，其余 `409 ORDER_STATUS_NOT_ALLOWED` |
| 订单 | `status=CANCELLED`，`cancelled_at` 非空 |
| 时段 | `reservation_slots` 为 0 |
| 日志 | 只有 1 条 `RESERVED -> CANCELLED` |

### 11.4 有限柜格竞争

| 观察项 | 通过条件 |
|---|---|
| 成功订单数 | 不超过实际可服务柜格数 |
| 同一柜格 | 同一时段最多 1 条占用订单 |
| 时段 | 无 `(cabinet_id, slot_start)` 重复 |
| 失败请求 | 409 冲突，不产生新订单/新时段 |

### 11.5 503 `LOCK_TIMEOUT` 的处理

`503 LOCK_TIMEOUT` 表示等待柜格行锁超时或死锁，不是正常的“柜格已被预约”。
如果并发压测出现 503：

- 先把它从“业务成功/冲突”统计中单独列出；
- 检查是否有长事务、慢 SQL、连接池耗尽、机器 CPU/内存饱和；
- 不要把它当作“防超卖成功”的证据，也不要用它推断业务规则正确。

### 11.6 压测资源与 MySQL 锁等待

压测时在 MySQL 会话执行：

```sql
SHOW GLOBAL STATUS WHERE Variable_name IN (
  'Threads_connected','Threads_running','Max_used_connections',
  'Innodb_row_lock_current_waits','Innodb_row_lock_waits',
  'Innodb_row_lock_time_avg','Innodb_row_lock_time_max',
  'Slow_queries','Questions','Aborted_connects'
);
SHOW GLOBAL VARIABLES LIKE 'max_connections';
SELECT COUNT(*) AS processlist_count FROM information_schema.PROCESSLIST;
```

判读：

- `Max_used_connections` 是启动以来峰值，不是当前连接数；当前值看 `Threads_connected` / `PROCESSLIST`。
- `Innodb_row_lock_waits` 是累计值，必须看压测前后的**增量**；`Innodb_row_lock_current_waits` 是采样瞬间仍在等待的数量。
- `Slow_queries=0` 只说明没有超过 `long_query_time` 的语句，不等于没有锁等待或没有性能问题。
- `mysqld` 以服务账号运行时，普通用户可能拿不到进程句柄；本次 `mysqld_cpu_pct` 的 WMI 读数不可靠，需结合整机 CPU、`Questions` 增量和行锁增量解释。
- 本次 20 线程补充运行的对应 CSV 在 `jmeter/results/same-20-resources.csv`，不要把这些短时读数写成容量/SLA。

## 12. Fiddler 抓包：本地 HTTP/HTTPS

### 12.1 安全边界

Fiddler 会完整保存请求和响应，包括：

- 登录请求体里的用户名、**明文密码**；
- 登录响应里的 `access_token`；
- 后续请求头里的 `Authorization: Bearer ...`；
- Cookie（本项目使用 Bearer Token，不是 Cookie 登录，但仍要检查）；
- 订单、手机号等业务数据。

因此：

1. 只在本地测试环境使用；
2. 使用专用测试账号，不使用真实用户密码；
3. 不截图未脱敏的登录请求/响应和 `Authorization`；
4. 不把 `.saz`、HAR、浏览器导出的 cURL 原样发给别人或提交到仓库；
5. 测试结束后关闭抓包；如不再需要，删除会话文件。

### 12.2 启动 Fiddler 并让本地回环流量经过它

本项目的本地地址通常是：

```text
http://127.0.0.1:8138/
http://127.0.0.1:8138/api/v1/...
```

默认端口以实际 `run.py` 为准；默认是 `8000`，测试环境可能改成了 `8138`。

Fiddler Classic 默认监听 `8888`：

1. `Tools > Options > Connections`，确认 `Fiddler listens on port` 为 `8888`；
2. 勾选 `Allow remote computers to connect` **只在确实需要时**开启；
3. 打开 `Capture Traffic`（F12）。

**回环地址的坑**

浏览器/系统代理经常会绕过 `localhost` / `127.0.0.1`。
如果 Fiddler 左侧完全看不到本地请求，任选一种方式：

**方式 A：使用 Fiddler 的本地回环主机名（Classic 常用）**

```text
http://localhost.fiddler:8138/
```

把页面入口换成这个地址，页面里的相对路径 `/api/v1/...` 仍会走同一主机。
Fiddler Everywhere 或不同版本对这个保留主机名的支持可能不同；
如果不生效，用方式 B。

**方式 B：给 Chrome/Edge 显式指定代理，并取消回环绕过**

先关闭已打开的浏览器，使用独立用户目录启动：

```powershell
& "$env:ProgramFiles\Google\Chrome\Application\chrome.exe" `
  --proxy-server="127.0.0.1:8888" `
  --proxy-bypass-list="<-loopback>" `
  --user-data-dir="$env:TEMP\fiddler-chrome"
```

Edge：

```powershell
& "${env:ProgramFiles(x86)}\Microsoft\Edge\Application\msedge.exe" `
  --proxy-server="127.0.0.1:8888" `
  --proxy-bypass-list="<-loopback>" `
  --user-data-dir="$env:TEMP\fiddler-edge"
```

启动后访问：

```text
http://127.0.0.1:8138/
```

如果仍然看不到，检查：

- Fiddler 是否真的在监听 8888；
- 浏览器是否被企业策略强制代理；
- 是否有 VPN/安全软件接管流量；
- 是否访问了 `https://` 但未开启 HTTPS 解密。

### 12.3 HTTPS（仅测试环境）

本项目本地默认是 HTTP，不需要解密 HTTPS。如果测试环境使用 HTTPS：

1. `Tools > Options > HTTPS`；
2. 勾选 `Capture HTTPS CONNECTs`；
3. 勾选 `Decrypt HTTPS traffic`；
4. `Actions > Trust Root Certificate`，按提示安装到当前用户/测试机；
5. 重启浏览器；
6. 确认 `https://` 请求在 Fiddler 中显示为可读的 HTTP 会话，而不是 `CONNECT` 隧道。

注意事项：

- 不要把 Fiddler 根证书安装到生产机或共享机器；
- 不要在代码里为了“让抓包通过”而关闭 TLS 校验；
- 如果目标站点有证书固定（certificate pinning），Fiddler 解密会失败，
  这时不要绕过安全机制，改用服务端日志/测试接口；
- 不抓包时关闭 `Capture Traffic`，减少敏感数据留存。

### 12.4 过滤，避免抓到无关流量

在 `Filters` 面板：

1. 勾选 `Use Filters`；
2. `Show only if URL contains` 填：

```text
127.0.0.1:8138
```

如果使用 `localhost.fiddler`，填：

```text
localhost.fiddler:8138
```

3. 只看接口时，可再加：

```text
/api/v1/
```

4. 用 `Hide if URL contains` 排除静态资源：

```text
.css
.js
.png
.jpg
.svg
.woff
```

抓包前按 `Ctrl+X` 清空旧会话；操作完成后立即停止抓包。

### 12.5 每个请求要检查什么

先在左侧会话列表看 `Result`、`Protocol`、`Host`、`URL`，
再选中会话，在右侧 `Inspectors` 面板逐项检查：

- 请求：`Headers` 看方法和头；`JSON` / `WebForms` / `TextView` 看请求体；
  `Raw` 看原始报文；
- 响应：`Headers` 看状态码和响应头；`JSON` / `TextView` 看响应体；
  `Raw` 看原始报文。

#### URL 与方法

- scheme：本地通常是 `http`；
- host/port：`127.0.0.1:8138`；
- path：例如 `/api/v1/auth/login`、`/api/v1/reservations`、
  `/api/v1/reservations/<order_no>/cancel`；
- query：例如分页 `page`、`page_size`、状态筛选 `status`；
- method：登录/创建/取消/签到/取件应为 `POST`，查询应为 `GET`；
- 状态码：`200/201/400/401/403/404/405/409` 等。

#### 请求头

重点看：

```http
Host: 127.0.0.1:8138
Accept: application/json
Content-Type: application/json
Authorization: Bearer <REDACTED>
Origin: <BROWSER_ORIGIN>
Referer: <BROWSER_PAGE>
User-Agent: <BROWSER_OR_TOOL>
```

检查点：

- 登录/注册请求不应带 `Authorization`；
- 预约、取消、签到、取件必须带 `Authorization: Bearer ...`；
- 创建/取消请求必须有 `Content-Type: application/json`；
- 签到/取件通常没有请求体，不应强行添加 JSON；
- 浏览器请求有 `Origin` / `Referer` / `Sec-Fetch-*`，接口工具没有，这是正常差异。

#### 鉴权信息

- 登录响应中的 `access_token` 是敏感信息，不要展示原值；
- 后续请求的 `Authorization` 只检查“存在且以 `Bearer ` 开头”，
  不要复制到聊天、文档、截图或在线 JWT 解码器；
- 前端把 token 存在 `localStorage` 的 `ll_access_token`，
  不要截图浏览器 `Application > Local Storage`；
- 测试结束调用 `POST /api/v1/auth/logout`，旧 token 会因 `token_version` 增加而失效；
- 如果只是验证鉴权，不需要把 token 写入任何文件。

#### 请求体

创建预约的请求体字段（实际模型）：

```json
{
  "cabinet_id": 11,
  "start_time": "2026-10-22T10:00:00",
  "end_time": "2026-10-22T11:00:00",
  "luggage_size": "LARGE",
  "idempotency_key": "manual-check-0001",
  "luggage_count": 1
}
```

检查：

- `cabinet_id` 是数字，不是字符串；
- `start_time` / `end_time` 是 ISO 8601 本地时间，分钟必须按 `slot_minutes` 对齐，
  秒必须为 `00`；
- `end_time > start_time`；
- `luggage_count` 本期只能是 `1`；
- `idempotency_key` 长度 8~64，重复提交必须使用同一个值；
- 取消请求体可为空，也可传：

```json
{"reason": "<TEST_REASON>"}
```

签到/取件不需要请求体。

#### 响应状态码与响应体

成功创建（新订单）：

```http
HTTP/1.1 201 Created
```

```json
{
  "order_no": "<ORDER_NO>",
  "status": "RESERVED",
  "idempotent_replay": false,
  "slot_count": 2,
  "start_time": "2026-10-22T10:00:00",
  "end_time": "2026-10-22T11:00:00"
}
```

幂等重放：

```http
HTTP/1.1 200 OK
```

```json
{
  "order_no": "<SAME_ORDER_NO>",
  "status": "RESERVED",
  "idempotent_replay": true
}
```

冲突：

```http
HTTP/1.1 409 Conflict
```

```json
{
  "code": "CABINET_TIME_CONFLICT",
  "message": "<MESSAGE>",
  "detail": {
    "cabinet_id": 11,
    "requested": {"start_time": "...", "end_time": "..."},
    "conflict": {"start_time": "...", "end_time": "...", "status": "RESERVED"}
  },
  "request_id": "<REQUEST_ID>"
}
```

响应头也要看：

```http
Content-Type: application/json
X-Request-Id: <REQUEST_ID>
```

如果是跨源请求，还可能出现：

```http
Access-Control-Allow-Origin: <BROWSER_ORIGIN>
```

检查点：

- 成功看 `order_no`、`status`、`slot_count`、`idempotent_replay`；
- 响应成功时 `Content-Type` 应为 `application/json`；
- 失败看 `code`，不要只匹配中文 `message`；
- 每个响应头应有 `X-Request-Id`；错误体也有 `request_id`，可用于查服务端日志；
- `request_id` 不是敏感信息，可以用于缺陷单；但不要连同 token 一起贴出；
- 不要因为响应头顺序、`Date`、`Server`、`Content-Length` 不同就判定接口不一致。

### 12.6 异常请求的实际行为基线

以下是 **2026-10-20 在本机 `127.0.0.1:8138` 实测** 的结果。
它们用于回归对照，不是对所有环境/版本的绝对承诺。

| 异常请求 | 实际 HTTP | 实际 `code` | 数据库影响 |
|---|---:|---|---|
| 不带 token 访问 `GET /reservations/my` | 401 | `AUTH_TOKEN_MISSING` | 无 |
| `Authorization: Bearer invalid.token.value` | 401 | `AUTH_TOKEN_INVALID` | 无 |
| `Authorization: Token abc`（方案不是 Bearer） | 401 | `AUTH_TOKEN_MISSING` | 无 |
| 错误密码 / 不存在的用户名登录 | 401 | `AUTH_INVALID_CREDENTIALS` | 无 |
| 登录请求体为空 `{}` | 400 | `VALIDATION_ERROR` | 无 |
| 创建预约 JSON 语法错误 | 400 | `VALIDATION_ERROR` | 无 |
| `Content-Type: text/plain` 提交 JSON | 400 | `VALIDATION_ERROR` | 无 |
| 创建预约缺少必填字段 | 400 | `VALIDATION_ERROR` | 无 |
| `cabinet_id` 传字符串 `"abc"` | 400 | `VALIDATION_ERROR` | 无 |
| 时间未按 30 分钟对齐 | 400 | `TIME_NOT_ALIGNED` | 无 |
| `end_time <= start_time` | 400 | `DURATION_OUT_OF_RANGE` | 无 |
| 开始时间过早 | 400 | `TIME_IN_PAST` | 无 |
| 小柜放 LARGE 行李 | 400 | `SIZE_NOT_MATCH` | 无 |
| 同一用户 + 同一幂等键重复提交 | 200 | 成功体，`idempotent_replay=true` | 不新增订单；仍 1 行 |
| 不同幂等键、同柜格重叠时段 | 409 | `CABINET_TIME_CONFLICT` | 不新增订单/时段 |
| 取消别人的订单 | 403 | `AUTH_FORBIDDEN` | 无 |
| 取消已取消订单 | 409 | `ORDER_STATUS_NOT_ALLOWED` | 无 |
| 开始前 30 分钟内取消 | 409 | `CANCEL_WINDOW_EXPIRED` | 无 |
| 签到窗口外签到 | 409 | `CHECKIN_WINDOW_INVALID` | 无 |
| 未签到直接取件 | 409 | `ORDER_STATUS_NOT_ALLOWED` | 无 |
| 查询不存在的订单号 | 404 | `RESOURCE_NOT_FOUND` | 无 |
| 对已存在路径使用错误方法（例如 `PUT .../cancel`、`POST /reservations/my`） | 405 | `VALIDATION_ERROR`，`detail="Method Not Allowed"` | 无 |
| `OPTIONS` 预检（带 Origin） | 200 | 无业务 code | 无 |

两个容易误判的点：

1. **`GET /api/v1/reservations` 返回的是 404，不是 405。**
   因为该精确路径没有 GET 路由；而 `POST /api/v1/reservations/my`
   或 `PUT /api/v1/reservations/<order_no>/cancel` 才会命中“路径存在、方法不对”的 405。
2. **参数校验失败是 400，不是 FastAPI 默认的 422。**
   本项目在 `app/core/errors.py` 中统一转成了 `400 VALIDATION_ERROR`。

### 12.7 失败请求不应留下数据

对每一个使用**新幂等键**的失败请求，核对：

```sql
SELECT
    r.id,
    r.order_no,
    r.status
FROM reservations r
WHERE r.idempotency_key = @idem;
```

预期 0 行。再核对：

```sql
SELECT COUNT(*) AS slot_rows
FROM reservation_slots s
JOIN reservations r
  ON r.id = s.reservation_id
WHERE r.idempotency_key = @idem;
```

预期 0。

如果失败请求使用了**已经成功过的幂等键**，返回 200 幂等重放是正常的，
这时应核对“仍然只有 1 条订单”，而不是要求 0 行。

### 12.8 浏览器请求与接口工具请求怎么对比

推荐使用同一账号、同一柜格、同一时间段、同一幂等键分别发一次，
然后按下面顺序对比。

#### 第一步：对齐可比条件

- 同一个后端实例和数据库；
- 同一个测试账号；
- 同一个 `cabinet_id`；
- 同一个 `start_time/end_time`；
- 同一个 `idempotency_key`；
- 同一个 `Content-Type`；
- 浏览器和接口工具都使用 `Authorization: Bearer ...`。

#### 第二步：对比“决定性字段”

| 对比项 | 浏览器 | Postman/curl | 是否必须一致 |
|---|---|---|---|
| 请求路径 | `/api/v1/...` | 同左 | 必须 |
| HTTP 方法 | `POST` | `POST` | 必须 |
| `Authorization` 是否存在 | 存在 | 存在 | 必须 |
| `Content-Type` | `application/json` | 同左 | 必须 |
| JSON 字段与值 | 同左 | 同左 | 必须（忽略字段顺序/空白） |
| 响应状态码 | 同左 | 同左 | 必须 |
| 业务 `code` | 同左 | 同左 | 必须 |
| `order_no` / `idempotent_replay` | 同左 | 同左 | 必须（动态值归一化后比较） |
| `Origin` / `Referer` | 有 | 通常无 | 不要求一致 |
| `User-Agent` | 浏览器 | 工具 | 不要求一致 |
| `Sec-Fetch-*` | 有 | 无 | 不要求一致 |
| `Accept-Encoding` | 浏览器自动 | 工具可能不同 | 不要求一致 |
| `Content-Length` | 自动 | 自动 | 不要求一致 |
| 请求头顺序/大小写 | 浏览器自动 | 工具自动 | 不要求一致 |
| `X-Request-Id` / `request_id` | 每次不同 | 每次不同 | 不要求一致 |
| `created_at` / 时间戳 | 动态 | 动态 | 归一化后比较 |
| Cookie | 本项目不应作为鉴权依据 | 通常无 | 不应依赖 |

#### 第三步：处理正常差异

浏览器的这些请求头是正常现象，不是接口差异：

```text
Origin
Referer
Sec-Fetch-Dest
Sec-Fetch-Mode
Sec-Fetch-Site
Upgrade-Insecure-Requests
sec-ch-ua
```

Postman/curl 的这些差异也正常：

```text
User-Agent: PostmanRuntime/...
Accept: */*
没有 Origin/Referer
可能没有 Accept-Encoding
```

不要把 `User-Agent`、头顺序、`Content-Length` 的差异当成缺陷；
真正需要一致的是：**URL、方法、鉴权存在性、Content-Type、业务请求体、
状态码、业务 code、关键响应字段和数据库事实**。

#### 第四步：处理 CORS/预检差异

- 浏览器从**同源**页面（`http://127.0.0.1:8138`）调用 `/api/v1`，
  通常没有 CORS 预检；
- 如果浏览器页面在另一个源，或接口工具显式带了跨源 `Origin`，
  可能出现 `OPTIONS` 预检；
- 对比时只比较预检之后的实际 `POST`，不要把 `OPTIONS 200` 与业务 `POST` 混在一起；
- 预检返回 200 不代表业务请求一定成功。

#### 第五步：用浏览器 Network 做交叉验证

Chrome/Edge DevTools：

1. `F12 > Network`；
2. 勾选 `Preserve log`、`Disable cache`；
3. 执行一次完整流程；
4. 点开请求，看 `Headers`、`Payload`、`Response`；
5. 右键请求 → `Copy` → `Copy as cURL`，得到与浏览器等价的命令。

`Copy as cURL` 会包含 `Authorization` 和登录请求体，**分享前必须脱敏**。
可以只保留结构，例如：

```bash
curl -X POST "http://127.0.0.1:8138/api/v1/reservations" \
  -H "Authorization: Bearer <REDACTED>" \
  -H "Content-Type: application/json" \
  --data '{
    "cabinet_id": 11,
    "start_time": "2026-10-22T10:00:00",
    "end_time": "2026-10-22T11:00:00",
    "luggage_size": "LARGE",
    "idempotency_key": "manual-check-0001",
    "luggage_count": 1
  }'
```

#### 第六步：把响应差异和数据库事实对上

例如浏览器和 Postman 都返回 201，但一个订单号不同：

- 如果使用了不同幂等键/不同用户/不同柜格，订单号不同是正常的；
- 如果使用完全相同条件，但返回两个不同订单号，说明幂等或测试数据隔离有问题；
- 最终用第 2~8 节的 SQL 查数据库，不要只比较响应 JSON。

抓包前：


2. 用测试账号登录，Fiddler 确认 `POST /auth/login` 返回 200；
3. 创建一个未来时段订单，记录响应中的 `order_no` 和 `idempotency_key`；
4. 执行第 2.1、2.2、2.3 节，确认订单、时段、柜格派生状态；
5. 用同一幂等键重复提交，确认 200 + `idempotent_replay=true`；执行第 4 节；
6. 用另一个幂等键提交重叠时段，确认 409 `CABINET_TIME_CONFLICT`；
   执行第 5 节，确认没有新订单；
7. 取消订单，确认 200、`released_slot_count=slot_count`；执行第 3、6 节；
8. 对未签到订单尝试取件，确认 409；对已签到订单执行取件，确认时段释放；
9. 用错误 token、错误方法、错误参数、错误用户分别发请求，对照 12.6；
10. 所有并发测试结束后，执行第 5、6、7、8、9 节的查询；
11. 清理本轮测试订单/用户/柜格，确认关键表回到基线。

## 14. 一句话判定规则

```text
201 新订单  → 订单 1 条 + 时段 = slot_count + 无重叠 + 日志 1 条创建
200 幂等    → 订单仍 1 条 + 同一个 order_no + 时段不翻倍
200 取消    → 状态 CANCELLED + cancelled_at 非空 + 时段 0 + 取消日志 1 条
200 取件    → 状态 COMPLETED + completed_at 非空 + 时段 0
409 冲突    → 不新增订单/时段，原占用保持不变
终态订单    → 不再占用任何时段
IN_USE/OVERDUE → 必须保留完整时段
503         → 单独作为环境/锁等待问题，不计入业务通过
```

HTTP 响应、Fiddler 会话和 SQL 结果三者一致，才算这条用例真正通过。
