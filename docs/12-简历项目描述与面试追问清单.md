### 1.3 30 秒项目介绍

> 我做的是一个智能行李寄存柜预约系统，用户按 30 分钟时段预约柜格，核心风险是同一柜格超卖、重复提交、取消后时段不释放，以及订单状态机不一致。  
> 我按“接口契约 → API 回归 → 浏览器链路 → 并发/数据库核验 → 缺陷回归”的顺序做测试，接口用 Postman 和 pytest，UI 用 Selenium，并发用 JMeter，最后用 MySQL 事实核对结果。

### 1.4 两分钟讲述模板

**背景：**  
这是一个行李寄存柜预约系统，用户选择寄存点、柜格和 30 分钟时段下单。业务上最关键的是时段冲突、幂等提交、取消释放和状态机，不能只看接口返回 200。

**我做了什么：**  
我先按 36 个 OpenAPI 操作和业务规则拆出 123 条用例，再分层落地：Postman 做接口契约和主流程，pytest 做可重复回归和数据库断言，Selenium 做真实浏览器链路，JMeter 做并发竞争，最后用 SQL 核对活动订单、slot、重复槽和状态日志。

**结果：**  
Postman 128 请求/311 断言通过；pytest API 71/71；Selenium Chrome 8/8；JMeter 8 组/104 样本，0 个 503、重复槽 0。缺陷方面留档了 3 个产品缺陷，D-01 接口 500、D-03 管理页无限重定向、D-04 M12 统计口径，均修复并回归。

**边界：**  
123 条用例目前有 2 条 Selenium + 26 条 B1 API 脚本执行记录，其余 95 条是自动化映射或待执行；JMeter 是同机小样本，不能外推为容量/SLA；第三阶段还有 4 个缺陷明细缺失。这些我会主动说明，不把“框架完成”说成“全量测试完成”。

### E. JMeter / 并发 / 数据库

- [ ] **Q27：JMeter 设计了哪些场景？**  
  回答：同一柜格竞争、有限柜格竞争、同一幂等键重复提交、并发取消，共 4 个场景。  
  证据：`docs/08` §4。

- [ ] **Q28：为什么是 8 组，不是 8 个场景？**  
  回答：4 个场景 × 初始/加压两档 = 8 组；线程数覆盖 4~24，共 104 个 HTTP 样本。  
  证据：`docs/08` §6.1。

- [ ] **Q29：409 为什么不算失败？**  
  回答：409 是预期的业务冲突，JSR223 断言允许预期响应进入成功；真正的通过条件是数据库事实，不是 JTL 的 `Err: 0`。  
  证据：`docs/08` §6.2、§7。

- [ ] **Q30：怎么证明没有超卖？**  
  回答：S1 活动订单 1、slot 2；S2 活动订单 6、slot 12；S3 只有 1 个订单；S4 取消后 slot 0；所有组重复 `(cabinet_id, slot_start)` 为 0。  
  证据：`verify-*.json`、`docs/10` §5.4。

- [ ] **Q31：0 个 503 说明什么？**  
  回答：说明本次没有出现 `LOCK_TIMEOUT`/连接耗尽；不等于高并发也没问题，不能外推容量。  
  证据：`docs/10` §5.5。

- [ ] **Q32：为什么样本这么少？**  
  回答：这是本机短时验证，重点看并发正确性，不是容量测试；样本少时 P95/P99 只能作为观测值。  
  证据：`docs/10` §5.7。

- [ ] **Q33：20 线程资源观测是什么？**  
  回答：单独补跑 S1 20 线程 × 2 循环，40 个请求样本，31.57 req/s，平均 432 ms，0 个 503；这部分不并入主结果 8 组/104 样本。  
  证据：`same-20.jtl`、`same-20-resources.summary.json`。

- [ ] **Q34：资源观测看到了什么？**  
  回答：8 个资源采样点；整机 CPU 峰值 13.06%，后端 CPU 峰值 7.81%/工作集 102.1 MB，JMeter CPU 峰值 282.81%/工作集 443 MB，MySQL 连接峰值 21/151，行锁等待 +38，慢查询 0。  
  证据：`docs/08` §6.4、`docs/10` §5.6。

- [ ] **Q35：为什么 JMeter CPU 超过 100%？**  
  回答：进程 CPU 是“单核百分比”，282.81% 约等于 2.8 个核；本机 16 个逻辑处理器，所以整机 CPU 只有 13.06%。  
  证据：`same-20-resources.summary.json`。

- [ ] **Q36：MySQL 的 CPU 为什么是 0？**  
  回答：mysqld 以服务账号运行，进程句柄被拒绝，WMI CPU 读数不可靠；所以用 `Questions` 增量、`Innodb_row_lock_waits` 和连接数判断活动，不拿 0 当“MySQL 空闲”。  
  证据：`docs/08` §6.4、`docs/09` §11.6。

- [ ] **Q37：能说系统支持 20/24 并发吗？**  
  回答：不能。20 线程只是 40 个请求、8 个资源采样点的本机诊断；没有独立压测机、长时间运行、GC 日志和逐锁快照，不能说容量/SLA。

- [ ] **Q38：数据库一致性怎么核对？**  
  回答：查活动订单、`reservation_slots`、不同柜格、重复槽、幂等键订单集合、取消后 slot 和状态日志；SQL 用实际表和字段，不假设不存在的“占用字段”。  
  证据：`docs/09`、`jmeter/tools/jmeter_data.py`。
