### 1.2 单条用例执行步骤

1. 确认前置数据和当前时间基准；需要造数时先记录原始值。
2. 执行接口/页面步骤，保存请求、响应、`request_id`、SQL 结果或截图。
3. 按四层判定：HTTP 状态、业务 `code`、关键字段、数据库事实。
4. 在 `docs/04` 的“实际”列写结论，不写“正常/OK”这种无法复核的词。
5. 失败时先判断是产品问题还是测试脚本/数据问题：
   - 产品行为与规则不符 → 建缺陷，写复现和证据；
   - 断言/等待/数据假设错误 → 修测试，重新执行。
6. 在本批次结束后清理测试数据，复查订单、slot、状态日志和临时用户/柜格为 0。
7. 更新 `docs/11` 的状态和证据路径；不要把“部分自动化”批量改成“已执行”。

## 4. 容量/SLA 测试计划（不是结果）

> 当前 20 线程 × 2 循环、8 个资源采样点只是本机短时诊断，不能当容量结论。容量测试必须另起一轮。

### 4.1 测试前定义

| 项 | 必须填写 |
|---|---|
| 目标接口/场景 | 例如 Q5/Q6 查询、创建预约、取消、混合读写 |
| 目标 SLA | P95、P99、错误率、503 上限、CPU/连接上限 |
| 压测机 | 独立机器，记录 CPU/内存/网络 |
| 被测环境 | 服务、MySQL、连接池、调度器状态 |
| 数据规模 | 寄存点/柜体/柜格/订单/用户数量 |
| 时长 | 预热 + 稳定运行 10~30 分钟 |
| 停止条件 | 503、错误率、P95、CPU、连接数、锁等待任一越界 |
| 证据 | JTL、HTML Dashboard、资源 CSV、MySQL 状态快照、GC 日志 |

### 4.2 建议梯度

| 阶段 | 线程 | 目的 |
|---|---:|---|
| 基线 | 1 | 单请求延迟和 SQL 基线 |
| 低并发 | 8 | 断言、数据准备、清理 |
| 中并发 | 16/24 | 观察锁等待和连接 |
| 目标并发 | 32/64 | 仅在低档稳定后进入 |
| 稳定性 | 目标并发 | 持续 10~30 分钟，不只看峰值 |
